# cross-boundary-foundations（越境の土台）

FDE、UXエンジニア、PdMがビジネスとUXとエンジニアリングの間に立ち、三つを両立させるためのスキル。

- 版：2026-10-09
- 作成者：なつ（note：art_reflection）
- 対象：Claude（Claude のアプリ、Claude Code など、スキルを読み込める環境）

## 何を支えるか

支える仕事は次のとおり。

- 顧客の業務にシステムやAIエージェントを入れる。PoCを本番に上げる
- 顧客の要望やヒアリングの内容を、仕様やPRDに落とす
- デザインを実装に渡す。コンポーネントや画面の状態と挙動を仕様にする
- KPIを決め、計測を仕込み、ダッシュボードの中身を決める
- 職能どうしの話が噛み合わないときに、両方の目的が残る分け方と決め方を出す
- 現場で分かったことを台帳に集め、ほかの顧客でも起きるものを見分けて、自社の製品への提案にする

扱う領域は0から9の段に並び、前の段が後ろの段の材料になる。9の気づきの台帳だけは、0から8の作業の途中で書き足していく。

| 段 | 決めること | 成果物（`assets/` のテンプレート） |
|---|---|---|
| 前 | 理想像から要求を立て、業務フロー、業務ルール、機能と画面、データ項目の順に降ろし、決まらずに残ることを0〜8に振り分ける | breakdown.md、interest-map.md |
| 0 | 何を知りたいか、KPI の式、見る人と次の行動 | kpi-definition.md |
| 1 | 用語と呼び方の対応 | glossary.md |
| 2 | 状態と遷移、誰が動かすか、AI に許す遷移 | state-table.md |
| 3 | 誰が何をできるか、AI が誰の権限で動くか | permission-matrix.md |
| 4 | 選択肢とコード値、AI の分類の定義 | taxonomy-sheet.md |
| 5 | 失敗の出し方と記録の仕込み | failure-inventory.md、tracking-plan.md、log-schema.json |
| 6 | 受け入れ条件と AI の評価の問題集 | acceptance-criteria.md |
| 7 | 判断の記録 | decision-record.md |
| 8 | ダッシュボードの定義と見る人 | dashboard-spec.md |
| 9 | 持ち帰る（還元）：気づきの台帳と製品への提案 | insight-log.md、product-feedback.md |

扱わないもの：画面そのものの作りと見た目、グラフの形と配色、どの層の価値を測るべきかという事業の判断。

## なぜ要るか

システムには、ログ、状態、権限、コード値といった決めごとがあります。これらはエンジニアが実装しながらよしなに決めていることが多いのですが、本当はビジネスやUXと深く絡んでいます。

たとえば、経費精算のシステムを作るとします。申請に領収書の添付漏れや金額の誤りがあると、経理の担当者はそれを申請者に戻して直してもらいます。これを「差し戻し」と呼びます。

顧客は「差し戻しを減らしたい」と言います。デザイナーは、経理が差し戻すときに理由を書ける入力欄を画面に置きます。エンジニアは、DB に「差し戻し済み」という印だけを残します。

半年後、顧客から「差し戻しの原因で一番多いのは何か」と聞かれます。調べようとすると、理由の欄は経理の担当者が自由に書いたままです。同じ「領収書がない」でも、ある人は「領収書なし」、別の人は「レシート添付忘れ」と書いています。100件並べると100通りの文になっていて、どの原因が多いのか数えられません。差し戻すときに「領収書なし」「金額の誤り」のようなタグを選んでもらっていれば、集計は一発で済んだはずです。

だから本当は、作る前に三者で次のことを一緒に決めておく必要がありました。顧客が知りたいのは原因ごとの件数なので、理由はタグで選ぶ形にする。そのタグを決まった値でDBに残す。タグごとの件数を毎月見る。

ほかにも、こういうことが起きます。

- 画面で編集ボタンを隠しても、APIからは審査中の申請を書き換えられてしまう
- 経費区分に「交際費」を足したら、去年の集計と比べられなくなる
- 送信がタイムアウトして「失敗しました」と出したが、実は登録済みで、申請者が送り直して二重申請になる
- AIが判定に迷った申請の行き先が決まっておらず、承認ボタンまでAIが押している
- 「審査が速くなった」と報告したいが、いつの時刻を記録すればよいかが決まっていない
- 前任者の作った画面がなぜこうなっているのか、誰も説明できない

決めないまま作っても、システムは動きます。困るのは本番に出てからで、過去のデータは戻らず、直すには移行の手間がかかります。

つまり、FDE、UXエンジニア、PdMは、ビジネスとUXの視点を持ってシステムを設計しなければいけません。それがこの役割の仕事です。そうして初めて、システムと事業の価値が両立します。

このスキルは、こうした決めごとを、ビジネス、UX、エンジニアリングの三つの目的を並べて検討するためのものです。扱うのは、KPIの式と計測、用語、状態、権限、選択肢とコード値、エラーとログ、受け入れ条件（AIなら評価の問題集）、判断の記録、ダッシュボードの定義と見る人の9つです。

このスキルを使うと、ビジネス、UX、エンジニアリングの目的を同じ表に並べて、整合性を取りながら検討できます。KPIで数えたいものは画面で選べる形になっているか。画面のラベルとDBの値は対応しているか。画面で隠した操作は、APIでも止まっているか。三つの目的がそろった表があれば、デザイナーもエンジニアも同じものを見て作れます。そうして作ったシステムは、そのまま事業の数字につながります。

## 誰のためか

- FDE（Forward Deployed Engineer）：顧客の現場に入って、システムや AI を業務に組み込む人
- UX エンジニア：デザインを動く実装に橋渡しする人
- PdM：事業とエンジニアのあいだで仕様を決める人

デザイナーや事業側が Claude にワイヤーや企画書を頼んだときも、その裏に決めごとが潜んでいれば、頼まれたものを仕上げたうえで、後から高くつく論点を3つまで添える。

## 入れ方

`cross-boundary-foundations.skill`（中身はこのフォルダの zip）を、使っている環境のスキルとして追加する。Claude のアプリなら設定のスキルの欄からアップロードする。Claude Code なら、このフォルダを `~/.claude/skills/` か、プロジェクトの `.claude/skills/` に置く。

## 頼み方の例

スキルの名前を出さなくても、こういう依頼で読み込まれる。

- 「経理は『差し戻しを減らしたい』、申請者は『入力を増やすな』と言っている。システムで何をどう決めればいい？」
- 「来週から顧客先に常駐して、問い合わせ対応に AI エージェントを入れる PoC をやる。最初の2週間で何を決めておけばいい？」
- 「PoC は精度8割くらい出てて顧客も乗り気。本番に上げる前にやっておくことを整理して」
- 「Figma の申込フローを実装する。デザインには正常系しか描かれてない。実装前に詰めることは？」
- 「デザインシステムの Button と FormField の状態（disabled、loading、error）を仕様にしたい」
- 「経費精算アプリのリニューアルで、何を KPI にしてどうログを取るかを決めたい」
- 「営業向けのダッシュボードを作りたい。受注率の数字が会議で毎回合わない」
- 「承認フローのステータスで、PM とエンジニアの会議が噛み合わない」

色や余白の調整、キャッチコピー、ペルソナ作り、グラフの見た目だけの依頼では読み込まれない。

## 揉めているとき

職能どうしが揉めているときは、利害の地図（interest-map.md）を使って、両方の目的が残る分け方と、誰がどう決めるかまで出す。

一つの案件で0から9を通した作例が `references/example-expense.md` にある。最初に読むならここがいちばん早い。

## 使う人がすること

特にない。Claude が仮決めして進めるので、違うと思ったところを言えば直る。Claude が聞いてくるのは、事業としての線引き（どの失敗なら許すか、何%の品質で出すか）と、取り返しのつかないもの（お金、個人情報、権限、消えるデータ）だけ。

## ほかのスキルとの関係

このスキルだけで完結する。次のスキルが入っていれば、Claude は役割を分けて使う。入っていなくても動く。

- 可視化のスキル（dataviz など）：ダッシュボードのグラフの形と配色
- UI を作るスキル：画面そのものの作り。このスキルは画面の裏の決めごとを受け持つ
- 文章のスキル（anti-ai-writing、japanese-native-writing など）：日本語の文章の点検

## 限界

- 調査ノートは、文ごとに【確認】（原文を開いて確かめた）、【未確認】（検索の要約しか見られなかった）、【解釈】の印を付けている。調べた環境では NN/g、Atlassian、Amazon の株主への手紙など多くの原典が開けなかった。【未確認】の内容を顧客に出す資料の根拠にするときは、原文で確かめてから使う
- 日本語で書いている。英語の依頼でも読み込まれるかは確かめていない
- 試したのは十数件の依頼で、採点は AI が行った。実際の案件での使い心地は、使いながら直していく前提

## 出典

段の5（エラーとログ）と0（何を知りたいか）は、note「UXデザイナー/PdMがKPIとログとエラーを理解しないとデータドリブンにならない」（art_reflection、2025年9月26日、https://note.com/art_reflection/n/n2458fe47b286）の考え方を土台にしている。そのほかの出典は各調査ノートの末尾にある。
