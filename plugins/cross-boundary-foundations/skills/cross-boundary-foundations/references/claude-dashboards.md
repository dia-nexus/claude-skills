# Claude Dashboards につなぐ

段8（見る場所）と段9（持ち帰る）で決めたことを、Claude Dashboards に写すときのノート。Claude Dashboards は2026年10月にベータで出た機能で、仕様は変わりうる。作るときは、その時点の Dashboard の型の指示とヘルプを正とし、このノートは「何をどこに写すか」の対応だけを受け持つ。

印：【確認】Dashboard の型の指示（Artifact の型「Dashboard」の SKILL.md）と、Claude ヘルプセンターの「Get started with Claude Dashboards」、claude.com の紹介記事を開いて確かめた（2026-10-09）。【未確認】二次情報だけで見た。【解釈】このスキルの考えに合わせてここで組み立てた。

## 何ができるか

- 自然言語で頼むと、接続したデータに対してグラフごとにクエリを書いて走らせ、ダッシュボードを作る。【確認】
- データ源は、Amazon Redshift、BigQuery、ClickHouse、Databricks、Snowflake などのデータウェアハウスと、Salesforce など Claude に接続したアプリ。CSV、TSV、JSON のファイルも添付できる（8MBまで）。【確認】
- どの数字も、出どころ（クエリ、ファイル、計算）をたどれる。グラフや数字を開くと、クエリ、変換、結果の行が見える。【確認】
- 各グラフに、データがいつ更新されたかが出る。ライブのクエリは自動で新しくなる。【確認】
- ライブのクエリは、見る人それぞれの接続で走る。見る人は、自分がもともと見られるデータしか見えない。【確認】
- 共有するまでは作った人だけが見られる。組織の外やリンクを知る人への共有は、管理者が許したときだけ。【確認】
- 深い分析は BI ツール（Amplitude、Grafana、Hex、Mixpanel、Omni、PostHog、Sigma など）に送る前提で、Dashboards 自体は素早い探索向け。【確認】
- ベータで、Pro、Max、Team、Enterprise で使える。Enterprise では既定で無効で、オーナーが Organization settings > Artifacts で有効にする。利用は使用量の上限に数えられる。【確認】

## このスキルの決めごととの対応

| このスキルで決めたこと | Dashboard でどこに写すか | 注意 |
|---|---|---|
| KPIの定義（段0）の指標名と式 | データセットのタイトルと説明、クエリの SQL | 式はクエリの中で計算する（同じ接続先の値どうしの割り算や結合は SQL で）。読む人がクエリを開いて確かめられるようにするため【確認】 |
| 用語集（段1）の指標の正本 | 接続先に意味の定義（semantic、governed な定義）があればそれを使う | 正本がそこにあれば、ほかの場所で見る数字と一致する【確認】。用語集の「正本の場所」の列にその名前を書く【解釈】 |
| 「完了」の数え方（段2の状態ID） | クエリの WHERE 句 | 状態IDで書き、画面のラベルで書かない【解釈】 |
| 見られる範囲（段3の権限） | ライブのクエリは見る人の接続で走るので、データ源の側の権限がそのまま効く。共有の範囲は Share で決める | ダッシュボードの側で隠すのではなく、データ源の権限と権限の表をそろえる【解釈】 |
| 個人情報を出さない（段3、段5） | 個人を特定する列を読まない。集計して出す | 型の指示も、頼まれていない個人の項目を読まないとしている【確認】 |
| 0件と「記録がない」（段8） | 型が、読み込み中、エラー、空を区別して表示する | 記録がない期間を0として描かない。クエリで0を埋めない【解釈】 |
| データの鮮度（段8） | 更新時刻が自動で出る。ファイルなら `updated` と `staleAfterHours` | ファイルで渡すと古くなる。変わるデータはライブのクエリにする【確認】 |
| 変更日の印（段4、段8） | 利用者が決めた固定の参照線は定数として描ける | 選択肢やプロンプトの版を変えた日を、変更履歴の表として持ち、データセットにして描くほうが崩れない【解釈】 |
| 線を割ったら誰に知らせるか（段8） | Dashboards の機能としては確かめられていない | 通知はダッシュボードの外で決める。dashboard-spec の「線を割ったら」の表はそのまま残す【未確認】 |
| 見る人と次の行動（段0、段8） | 画面の見出しや注記として書ける | 「数字が動いたら誰が何をするか」を各グラフの近くに一行で書く【解釈】 |

## 段9：気づきと回避策を見る場所にする

示唆を出すための基盤として、二つのダッシュボードが作れる。【解釈】

1. **案件の中で回避策を見るダッシュボード**：トラッキングプランの「回避策と示唆のイベント」（`list_exported`、`other_option_selected`、`ai_decision_overridden`、`permission_exception_requested`、`free_text_note_added`）を、イベントのテーブルからライブのクエリで集計する。週ごとの件数と、画面や項目ごとの内訳を置く。件数が増えた週は、台帳に一行足す合図になる。
2. **案件をまたいで気づきを束ねるダッシュボード**：`scripts/insight_digest.py --csv` の出力（タグごとの案件数、根拠の数、見立て）を、添付ファイルのデータセットにする。台帳を見直すたびにファイルを差し替える。顧客名や個人名が入っていないことを、`insight_digest.py` の点検で確かめてから添付する。添付したファイルは、ダッシュボードを開ける人なら誰でも読める。【確認】

どちらも、見る人と次の行動を先に決める。前者は案件の担当が毎週見て台帳に足す。後者は製品の側と月に一度見て、持ち帰りの提案にする行を選ぶ。

## 使うかどうかの判断

- Claude Dashboards が使える環境（Artifact の型に Dashboard がある、または利用者が使えると言った）で、データが接続先にあるなら、dashboard-spec.md を書いたあとに、そのまま作ることを提案する。作るときは Dashboard の型の指示に従う。
- 接続先がなく、データが手元のファイルだけなら、添付ファイルで作れる。ただし古くなるので、更新の担当と頻度を決める。
- 本番で長く使い、通知や細かい権限が要るなら、BI ツールに送る前提で、dashboard-spec.md を正本として残す。
- 使えない環境なら、dashboard-spec.md までで止め、グラフは可視化を受け持つ人やスキルに渡す。
