# リサーチノート ①状態とステータスの設計（ステートマシン）

作成日：2026-10-07
凡例：
- 【確認】出典を実際に開いて確かめた事実
- 【未確認】出典を開けなかった、または検索結果の要約しか見ていないもの。内容は参考扱い
- 【解釈】調査者の考え。出典の裏づけはない

調査環境についての注記：この調査環境からは stately.ai、docs.temporal.io、martinfowler.com、nngroup.com、sciencedirect.com、wikipedia.org、leanpub.com などへの直接アクセスが遮断されていた。公式ドキュメントが GitHub 上に原文として置かれているもの（XState / Stately のドキュメント、Temporal のドキュメント、Google AIP、Microsoft Architecture Center、GOV.UK Design System、PostgreSQL のドキュメント原稿）は GitHub 経由で原文を開いた。開けなかったものは【未確認】として扱い、検索結果に出た要約の範囲を超えて書いていない。

## 0. 定義と範囲

**この領域が扱うもの**
注文・申請・案件・アカウント・コンテンツなど、「時間とともに段階が進むもの」について、
1. どんな状態があるか（状態の一覧と名前）
2. どの状態からどの状態へ移れるか（遷移）
3. 何がきっかけで移るか（イベント：人の操作、時間切れ、外部システムの通知）
4. どんな条件なら移ってよいか（ガード）
5. 移るときに何が起きるか（副作用：通知、課金、在庫引当、ログ）
6. 誰がその遷移を起こしてよいか（②権限と接する）
を決めること。

**基本用語**
- 状態機械（ステートマシン）：【確認】XState のドキュメントは「状態機械は、イベントが起きたときにプロセスがある状態から次の状態へどう移るかをモデル化する」「状態機械は同時に一つの状態にしかなれない」「イベントが遷移を起こす」と定義している。(S2)
- ステートチャート：【確認】同ドキュメントは「ステートチャートは従来の有限状態機械を拡張し、より複雑なロジックを表す」もので、階層・並行・通信を加えたものと説明している。(S2) statecharts.dev は「状態が階層を持てる。各状態がその下に別の状態機械（サブステート）を持てる」点を主な特徴としている。(S5c)
- 起源：【未確認】David Harel「Statecharts: A Visual Formalism for Complex Systems」(Science of Computer Programming, 1987)。従来の状態遷移図に階層・並行（直交）・通信（ブロードキャスト）の3要素を加えたという要旨は、複数の二次資料（検索結果）で一致しているが、論文本文（ScienceDirect、Weizmann 研究所のPDF）は開けなかった。
- ガード：【確認】「イベントを処理するときに機械が確かめる条件関数。真なら遷移に進む」。ガードは「純粋で同期的な、真偽を返す関数であるべき」。(S3)

**範囲の線引き【解釈】**
- ①は「時間の軸に沿った変化の規則」。②権限は「誰が」、③分類体系は「状態の値をコードとしてどう管理するか」、④概念モデルは「状態を持つのはどの概念か」、⑤受け入れ条件は「遷移ごとの期待結果」、⑥設計判断の記録は「なぜこの切り方にしたか」。①はこの5つすべてと接するハブになりやすい。
- 「ステータス」という言葉は、(a) データ上の状態値、(b) 画面に出す表示ラベル、(c) KPIとして数える段階、の3つを混同しやすい。この3つを別物として扱うことが、この領域の議論の出発点になる。

## 1. エンジニア視点（11項目）

### E1. 状態と遷移を「表」として明示する（暗黙のif文に散らさない）
- 何を：状態一覧、遷移（元→先）、イベント、ガード、副作用を一つの定義（遷移表やステートチャート定義）に集める。
- なぜ：【確認】statecharts.dev は、状態機械を使うと全状態が洗い出され、挙動が明示的になる利点を挙げている（benefit 系ページ群のタイトルと、QA が図を「たどれる地図」として使えるという記述）。(S5b, S5d) 【解釈】if文に散らすと「この状態でこのボタンを押したら？」に誰も即答できなくなる。
- 悪い例→良い例：`if (order.paid && !order.shipped && !order.cancelled)` が画面ごとに書かれている → `order.state === "paid"` と、`paid` から出られる遷移の一覧が一か所にある。
- 出典：S2, S5b, S5d

### E2. 状態の爆発をステートチャートの階層・並行で抑える
- 何を：独立した性質（例：支払状態と配送状態）を一つの列挙型に掛け合わせず、並行状態や階層に分ける。
- なぜ：【確認】statecharts.dev は「新しい側面を状態機械に加えると、必要な状態の数が掛け算で増え、遷移の数も不釣り合いに増える」と説明し、対策として並行状態（独立した変数を別々に扱い、増え方を掛け算から足し算にする）、階層（依存する性質を関係する文脈の中だけに置く）、ガード（状態を増やさず条件で分岐する）を挙げている。(S5a)
- 悪い例→良い例：`PAID_NOT_SHIPPED` `PAID_SHIPPED` `UNPAID_NOT_SHIPPED`… → `payment: unpaid|paid|refunded` と `fulfillment: pending|shipped|delivered` を並行で持つ。
- 出典：S5a, S2

### E3. ステータス列は直接書き換えさせない。遷移は専用の操作で行う
- 何を：状態フィールドは出力専用とし、`publish` `cancel` のような名前のある操作（メソッド／エンドポイント）経由でのみ変える。
- なぜ：【確認】Google AIP-216 は「State 列挙型を update メソッドで直接更新させるべきでない（create で直接設定もさせない）」とし、状態変更は `PublishBook` のような専用メソッド（`:publish` のようなカスタム動詞）で行い、不正な遷移には `FAILED_PRECONDITION` を返すとしている。状態フィールドは「Output only」として扱う。(S6) 【確認】django-fsm は状態フィールドへの直接代入を防ぎ、遷移メソッド経由でのみ変える仕組みを持ち、許されない遷移では `TransitionNotAllowed` を投げる。(S15)
- 悪い例→良い例：`PATCH /orders/1 {status: "shipped"}` → `POST /orders/1:ship`（元の状態が `paid` でなければエラー）。
- 出典：S6, S15

### E4. 不正な遷移はデータ層の手前で必ず弾き、理由を返す
- 何を：遷移ごとに「元の状態の条件」と「ガード」を検証し、失敗時は例外か明示的なエラーで返す。
- なぜ：【確認】AASM（Ruby）はガードが偽なら遷移を拒否し `AASM::InvalidTransition` を投げる（設定で false を返すだけにもできる）。`may_run?` のように「今この遷移が可能か」を問い合わせるメソッドと、`permitted_transitions` で現在可能な遷移一覧を返す機能を持つ。(S14)
- 悪い例→良い例：画面側でボタンを隠すだけ → サーバー側でも同じ規則で検証し、画面は `permitted_transitions` を見てボタンを出す（規則が一か所になる）。
- 出典：S14, S6

### E5. 状態名は「形容詞・過去分詞」で、安定した状態と処理中の状態を区別する
- 何を：`ACTIVE` `SUSPENDED` のような落ち着いた状態と、`CREATING` `DELETING` のような一時的な処理中状態を分けて名付ける。既定値（未設定）を利用者に見せない。
- なぜ：【確認】AIP-216 は落ち着いた状態の例として `ACTIVE` `SUCCEEDED` `FAILED` `DELETED` `SUSPENDED`、処理中の例として `CREATING` `RUNNING` `DELETING` `PENDING` を挙げ、既定値 `STATE_UNSPECIFIED` を利用者に見せるべきでないとしている。単純な二値なら状態列挙型ではなく `delete_time` のようなタイムスタンプで足りる場合があるとも書いている。(S6)
- 悪い例→良い例：`status: "process"`（動詞・曖昧）→ `state: PROCESSING`（処理中）と `state: COMPLETED`（完了）。「削除済みかどうか」だけなら `deleted_at`。
- 出典：S6

### E6. 列挙型の値は「減らせない」前提で設計する
- 何を：DBの列挙型やコード値は、追加はできても削除・並べ替えが難しいことを前提に、最初の状態の切り方を慎重に決め、廃止値の扱い（非推奨化）を決めておく。
- なぜ：【確認】PostgreSQL のドキュメントは「列挙型は主に静的な値の集合を想定しているが、既存の列挙型への値の追加と改名はできる」「既存の値は削除できず、並び順も変えられない。列挙型を削除して作り直さない限り」と書いている。(S16)
- 悪い例→良い例：UXの要望で表示ラベルが変わるたびにDBの列挙値を足す → DB の状態値とは別に、表示ラベルの対応表を持つ（③分類体系と連携）。
- 出典：S16

### E7. 遷移の履歴を残す（現在値だけを上書きしない）
- 何を：現在の状態列に加えて、「いつ・誰が・どのイベントで・どの状態からどの状態へ」を追記専用で記録する（履歴テーブル、またはイベントソーシング）。
- なぜ：【確認】Microsoft のイベントソーシングパターンは「オブジェクトに対して行われた一連の操作を追記専用のストアに保存する」もので、イベントは不変であり、イベントを再生して現在の状態をいつでも再構築できる、監査に使えると説明する。一方で、単純なCRUDや短命な試作には向かず、結果整合性が本質的に伴う、イベントを直す唯一の方法は打ち消しのイベントを足すこと、と注意も書いている。(S12) 【確認】AASM には状態に入った時刻を `<state>_at` 列に自動で入れるオプションがある。(S14) 【未確認】Martin Fowler の「Event Sourcing」(2005) はアプリケーション状態のすべての変更をイベントの列として捉えるパターンとして知られるが、本文は開けなかった。
- 悪い例→良い例：`status` 列を上書きするだけ → `order_state_transitions(order_id, from, to, event, actor, at)` に追記し、現在値はその最新行と一致させる。全面的なイベントソーシングは必要なときだけ。
- 出典：S12, S14（Fowler は未確認）

### E8. 並行更新は楽観ロック（etag / バージョン）で守る
- 何を：遷移の要求に「読んだ時点のバージョン」を付け、更新時に一致しなければ失敗させる。
- なぜ：【確認】EF Core のドキュメントは、楽観的並行制御を「競合はまれと仮定し、ロックを取らず、読んだ後にデータが変わっていたら保存を失敗させる」方式と説明し、競合時に `DbUpdateConcurrencyException` を投げるので、アプリ側で捕まえて扱う必要があるとする。(S13) 【確認】AIP-154 は etag が一致しなければ `ABORTED`（HTTP 409）を返すべきとしている。(S7) 【確認】django-fsm には楽観ロック用の `ConcurrentTransitionMixin` がある。AASM には悲観ロック（`requires_lock`）の設定がある。(S14, S15)
- 悪い例→良い例：担当者Aが「承認」、Bが「差し戻し」を同時に押し、後勝ちで黙って上書き → 後から押した側に「他の人が先に更新しました」と返し、最新状態を見せる。
- 出典：S13, S7, S14, S15

### E9. 遷移の要求は冪等にする（再送しても二重に進まない）
- 何を：遷移を起こすリクエストにリクエストIDを付け、同じIDの再送には前回の結果を返す。
- なぜ：【確認】AIP-155 は「リクエストIDを渡したら冪等性を保証しなければならない」「重複を検知したら、前回成功したリクエストの応答を返すべき（クライアントは前回の応答を受け取れなかった可能性が高いため）」としている。(S8) 【確認】Microsoft のイベントソーシングパターンは、イベントの配信は通常「少なくとも1回」なので、受け手は同じイベントを複数回受け取りうると注意している。(S12)
- 悪い例→良い例：決済完了通知が2回届き、「発送待ち」に2回進んで在庫を2回引き当てる → イベントIDで重複を弾き、2回目は何もしない。
- 出典：S8, S12

### E10. 複数サービスにまたがる遷移は Saga（補償）で設計し、「戻れない点」を明示する
- 何を：注文確定→決済→在庫→配送のように複数のサービスが関わる流れは、ローカルトランザクションの連鎖として設計し、失敗時の打ち消し操作（補償）を決める。
- なぜ：【確認】Microsoft の Saga パターンは、分散した処理を「ローカルトランザクションの連続」に分け、失敗時は先行ステップを逆の操作（補償トランザクション）で打ち消すと説明する。「ピボットトランザクション」を境にそれ以降は打ち消せず、再試行可能な操作で必ず完了させる。分離性がないため、更新の消失やダーティリードが起こりうるので、セマンティックロック（更新中であることを示すアプリ側の印）などで対処するとしている。コレオグラフィは単純な流れに向くが複雑になると循環依存が起きやすく、オーケストレーションは中央の制御役を置く代わりにその部分が単一障害点になる。(S11)
- 悪い例→良い例：「キャンセル」がどこまで可能かを誰も知らない → 「発送指示を出した時点（ピボット）より前は全額返金で取り消し可、以降は返品フローへ」と遷移図に書く。
- 出典：S11

### E11. 長く続く・人を待つ流れはワークフローエンジンに任せ、決定性を守る
- 何を：数日から数週間かかる申請や、承認待ち・期限切れを含む流れは、Temporal のような永続実行のワークフローエンジンで状態を持たせる。
- なぜ：【確認】Temporal の README は「永続実行（durable execution）プラットフォーム」で、一時的な障害を自動で扱い、失敗した操作を再試行するとしている。(S10b) 【確認】Temporal のドキュメント（GitHub上の原文）は、ワークフローのコードは「同じ入力なら同じAPI呼び出しを同じ順で行う」ようにしなければならず、再実行時に生成されたコマンドを既存のイベント履歴と照合し、食い違えば非決定性エラーになると説明する。原因の典型はコード変更や乱数分岐。(S10a)
- 悪い例→良い例：cron で「期限切れ」を毎晩まとめて判定し、途中で落ちると一部だけ更新される → ワークフロー内でタイマーを持ち、期限が来たら「期限切れ」へ遷移させる。ワークフローのコードを変えるときはバージョンを分ける。
- 出典：S10a, S10b

### E12. 処理に時間がかかる遷移は「処理中」状態と進捗の器を用意する
- 何を：完了までに時間がかかる操作は、すぐに「受付済み・処理中」を返し、完了の有無と進捗を別に問い合わせられるようにする。
- なぜ：【確認】AIP-151 は、時間がかかる可能性のあるメソッドは Operation を返し、`done` で完了を示し、metadata に進捗や部分的な失敗の情報を入れるとしている（目安は概ね10秒以上）。(S9)
- 悪い例→良い例：申請送信のリクエストが30秒ブロックし、タイムアウトして利用者が再送 → 「受付済み（審査中）」を即返し、画面はそれを表示する（UX視点 U5 と対）。
- 出典：S9

## 2. ビジネス・UX視点（10項目）

### U1. 「データの状態」「画面のラベル」「KPIの段階」を分けて設計する
- 何を：同じ「ステータス」でも、システムが持つ状態値、利用者に見せる表示、ビジネスが数える段階の対応表を作る。
- なぜ：【解釈】内部の状態は検証や副作用の都合で細かくなりがちで、それをそのまま画面に出すと利用者には意味が分からない。逆に画面の都合でDBの状態を増やすと E6 の通り戻しにくい。対応表があれば、表示文言の変更が実装を壊さない。
- 悪い例→良い例：DB の `PENDING_FRAUD_REVIEW` が画面に出る → 画面は「確認中（通常1営業日）」、KPIは「審査段階」として数え、対応表で紐づける。
- 出典：【解釈】（裏づけとして AIP-216 が状態フィールドを内部の規則として扱う点 S6、GOV.UK が表示は最小限のステータスから始めよとする点 S17a）

### U2. 表示するステータスの数は、最小から始めて調査で増やす
- 何を：利用者に見せるステータスの種類は少なく始める。
- なぜ：【確認】GOV.UK Design System の Tag は「ステータスを増やすほど利用者は覚えにくくなる。うまくいきそうな最小の数から始め、ユーザーリサーチで必要と分かったら増やす」と書いている。ステータス名は動詞ではなく形容詞にし、タグをリンクやボタンにしない、色だけで情報を伝えない（WCAG 1.4.1）、とも。(S17a)
- 悪い例→良い例：内部の8状態をすべてタグで出す → 「対応が必要」「確認中」「完了」の3種から始める。
- 出典：S17a

### U3. 手続きの全体像と「今どこか」「まだ始められない理由」を見せる
- 何を：複数ステップの申請では、各ステップのステータスを一覧にし、依存関係で着手できないものは「まだ始められません」と見せる。
- なぜ：【確認】GOV.UK の Task list は、「完了」「未完了」「まだ始められない」などのステータスで、利用者がどれだけ終えて、あとどれだけ残っているかを一目で把握できるようにする。研究の結果、大文字表記は読みにくいので文頭のみ大文字に変え、「完了」の見た目を控えめにして対応が必要なタスクに注意が向くようにした。文言が利用者にとって最適かはまだ検証中としている。(S17b)
- 悪い例→良い例：グレーアウトしたボタンだけで説明がない → 「前のステップの本人確認が終わると始められます」。
- 出典：S17b

### U4. 状態が変わった直後の画面で「次に何が、いつ起きるか」を伝える
- 何を：申請・注文の確定後に、受付番号、次に起きること、その時期、問い合わせ先を出す。
- なぜ：【確認】GOV.UK の Confirmation pages パターンは、参照番号（あれば）、次に何がいつ起きるか、サービスの連絡先を含めるとしている。(S17c) 【未確認】NN/g のヒューリスティック1「システム状態の可視性」は「適切なフィードバックを妥当な時間内に返し、何が起きているかを利用者に常に伝える」とされる（検索結果の要約のみ。本文は未読）。
- 悪い例→良い例：「送信しました」だけ → 「受付番号 A-1234。審査結果は5営業日以内にメールで届きます。届かない場合はこちら」。
- 出典：S17c（NN/g は未確認）

### U5. 待ちの見せ方を「進み具合が分かるか」で選ぶ
- 何を：所要時間や進捗が分かる処理は割合で、分からない処理は不定形のインジケーターで見せる。同じ種類の処理には同じ見せ方を使う。
- なぜ：【確認】Material Design（Android 実装のドキュメント）は、確定型は「進捗と待ち時間が分かるとき」、不確定型は「分からないとき」に使い、同じ種類の操作にはアプリ内で一つの型だけを使うとしている。(S18) 【未確認】NN/g「Progress Indicators Make a Slow System Less Insufferable」は、進捗表示がシステムが動いていることを伝え不確かさを減らすこと、最後で止まると満足度が下がることを述べているとされる（検索結果の要約のみ）。
- 悪い例→良い例：数日かかる審査にスピナーを出し続ける → 「審査中（平均3日）」という状態表示に切り替える。スピナーは数秒の処理だけ。
- 出典：S18（NN/g は未確認）

### U6. 例外の状態（保留・差し戻し・取消・期限切れ）を正常系と同じ重さで設計する
- 何を：ハッピーパスだけでなく、差し戻し、取り消し、期限切れ、保留、失敗からの再開を状態図に描き、それぞれの画面と文言、利用者にできること（再提出、問い合わせ）を決める。
- なぜ：【確認】statecharts.dev は「異常の扱い（handle anomalies）」を状態機械の利点の一つに挙げている（ページ名の確認のみ、本文は未読）。(S5 一覧) 【確認】Saga パターンでは、どの時点まで取り消せるか（ピボット）が設計上の論点になる。(S11) 【解釈】問い合わせが集まるのは、たいてい例外の状態で「なぜこうなったか」「何をすればよいか」が画面にないときである。
- 悪い例→良い例：差し戻しが「未提出」に戻るだけで理由が出ない → 「差し戻し（要修正）」を独立した状態にし、理由と修正箇所を表示する。
- 出典：S11, S5（一覧）、【解釈】

### U7. 状態の切り方が問い合わせと離脱を生むことを、ジャーニーに重ねて確かめる
- 何を：カスタマージャーニーの各段階に、システムの状態を重ねた図を作り、「利用者が不安になる区間」（状態が長く変わらない、説明がない）を探す。
- なぜ：【未確認】NN/g は「Status Trackers and Progress Updates: 16 Design Guidelines」で、ステータストラッカー（利用者が見に行く pull）と進捗通知（システムから届く push）を区別しているとされる（検索結果の要約のみ）。【解釈】内部では「出荷準備中」が3日続くのは正常でも、利用者は止まっていると感じて問い合わせる。状態を一つ分ける（「倉庫で梱包中」）か、状態は変えずに期待時間を出すかは、問い合わせ件数で判断できる。
- 悪い例→良い例：問い合わせ理由の上位が「今どうなってますか」→ その区間に中間の表示状態か期待時間を足し、問い合わせ件数の変化を測る。
- 出典：【解釈】（NN/g は未確認）

### U8. KPIの「必須通過点」は状態遷移として計測できる形にしておく
- 何を：ファネルやリードタイムを測りたい段階（申込→審査→承認→初回利用）は、状態遷移として記録され、時刻が残るようにする。
- なぜ：【確認】AASM の `<state>_at` タイムスタンプのように、状態に入った時刻を残す仕組みがある。(S14) 【未確認】プロセスマイニングでは、イベントログの各イベントがケース（案件）・アクティビティ・時刻を持つことが最低条件とされる（van der Aalst の資料。検索結果の要約のみ）。【解釈】状態遷移の履歴（E7）がそのままファネル分析とリードタイム分析の素材になる。逆に、画面の表示だけで段階を作り、データに遷移が残らない設計だと後から測れない。
- 悪い例→良い例：「審査に何日かかっているか」を担当者の手集計で出す → 遷移履歴から自動で出る。
- 出典：S14（プロセスマイニングは未確認）

### U9. 状態の名前は「誰の言葉か」を決めてから付ける
- 何を：内部の状態名（エンジニアとドメイン専門家が使う）と、利用者向けの文言（UXライティング）の決定権者を分け、対応表で管理する。
- なぜ：【確認】AIP-216 は状態名の付け方（形容詞、接頭辞を付けない）を規則化している。(S6) GOV.UK は利用者向けの名前を形容詞にし、文言が利用者に最も分かりやすいかは検証中としている。(S17a, S17b) 【解釈】状態名は④ドメイン用語の一部であり、名前の決定を実装者の命名に任せると、ビジネス側の言葉とずれたまま定着する。
- 悪い例→良い例：エンジニアが付けた `HOLD2` が業務マニュアルにまで広がる → Event Storming 等で業務の言葉を決め（6章）、内部名と利用者向け文言を両方記録する。
- 出典：S6, S17a, S17b

### U10. 利用者が自分で状態を動かせる範囲（取り消し、やり直し）を明示する
- 何を：利用者が自分で起こせる遷移（取り消し、編集、再提出）と、起こせない遷移を画面で区別し、起こせない場合は理由を出す。
- なぜ：【確認】AASM の `may_xxx?` や `permitted_transitions` のように、現在可能な遷移を問い合わせる仕組みがある。(S14) 【解釈】この一覧を画面に使えば、「なぜキャンセルボタンがないのか」を状態から説明できる（「発送手配後のため、取り消しではなく返品になります」）。
- 悪い例→良い例：キャンセルボタンが急に消える → 「発送手配が始まったため、ここからは返品手続きになります」と表示。
- 出典：S14、【解釈】

## 3. AI視点（8項目）

### A1. 状態と遷移の定義を、AIエージェントが読める「地図」として公開する
- 何を：遷移表・ステートチャートを、機械可読な定義（XState の定義、JSON、APIのカスタムメソッド一覧）として持ち、エージェントに「今の状態」と「今可能な遷移」を渡す。
- なぜ：【確認】Stately Agent は「機械がエージェントにできることを定める」「モデルはイベントを提案し、機械がそれが許されるか、次に何が起こるかを決める」と説明し、「無効なエージェントの行動を不可能にする」ことを掲げる。返金の例では、金額が100ドルを超えると自動返金のイベントをガードが拒否し、判断をやり直させる。(S4)
- 悪い例→良い例：エージェントに「注文管理APIを自由に使ってよい」と渡す → 現在の状態から可能な遷移だけをツールとして渡す。
- 出典：S4

### A2. AIに許す遷移は「システム側」で制限する（AIの判断に任せない）
- 何を：エージェントが起こせる遷移を権限で絞り、影響の大きい遷移（取消、返金、公開、削除）は人の承認を挟む。許可の判定は下流のシステムで行う。
- なぜ：【確認】OWASP LLM06「過剰なエージェンシー」は、原因を過剰な機能・過剰な権限・過剰な自律性の3つとし、対策として拡張機能の最小化、影響の大きい行動の前に人の承認を求めること、「行動が許されるかをLLMに決めさせるのではなく、下流のシステムで認可を行う」ことを挙げる。(S22) 【確認】MCP の仕様（2025-06-18）は「ツールの呼び出しを拒否できる人間が常にループの中にいるべき」とし、ツール注釈は信頼できるサーバーからでない限り信頼しないものとして扱うよう求めている。(S21)
- 悪い例→良い例：プロンプトに「500ドル以上の返金はしないでください」と書く → 返金の遷移のガードに金額条件を入れ、超えたら「承認待ち」状態へ遷移させる。
- 出典：S22, S21, S4

### A3. LLMのワークフローは、決まった道筋は「ワークフロー」、決められない部分だけ「エージェント」にする
- 何を：手順が決まっている部分はコードで状態遷移を固定し、手順を事前に決められない部分だけをLLMの自律判断に任せる。
- なぜ：【確認】Anthropic「Building effective agents」は、ワークフローを「LLMとツールがあらかじめ定めたコードの道筋で編成されるもの」、エージェントを「LLMが自分の処理とツール利用を動的に決めるもの」と区別し、エージェントは手順の数が予測できない、道筋を固定できない問題に向くとする。自律性は費用と誤りの累積を伴うので、サンドボックスでの試験と適切なガードレールを勧め、チェックポイントや行き詰まったときに人のフィードバックを待つべきとしている。(S20)
- 悪い例→良い例：申請審査の全工程をエージェントに任せる → 「受付→書類チェック（LLM）→不足時は差し戻し→人が承認」を状態図として固定し、書類チェックの中だけLLMを使う。
- 出典：S20

### A4. エージェント自身の実行状態も永続化し、中断・再開・人の介入をできるようにする
- 何を：長く動くエージェントは、途中の状態を保存し、失敗や人の確認待ちから再開できるようにする。
- なぜ：【確認】LangGraph の README は、障害を越えて長時間動き「中断したところから自動で再開する」永続実行と、実行中の任意の時点でエージェントの状態を確認・修正できる human-in-the-loop を特徴として挙げる。(S23) 【確認】Temporal は失敗した操作の自動再試行を持つ永続実行基盤であり (S10b)、Stately Agent も「決定的・検査可能・再開可能」を掲げる。(S4)
- 悪い例→良い例：エージェントの途中経過がメモリ上にしかなく、落ちると最初からやり直し、外部への副作用が二重に起きる → 状態をチェックポイントとして保存し、副作用は冪等にする（E9）。
- 出典：S23, S10b, S4

### A5. 状態遷移の履歴を、分析と学習のデータ資源として整える
- 何を：遷移履歴に「案件ID・イベント・前後の状態・時刻・実行者（人／AI／システム）・理由」を必ず残す。
- なぜ：【確認】イベントソーシングでは、イベントを再生して過去の状態を再構築でき、監査に使える。(S12) 【未確認】プロセスマイニングの最低条件は、各イベントが案件・アクティビティ・時刻を持つこと（検索結果の要約のみ）。【解釈】この形で残しておけば、ボトルネック分析、差し戻し理由の分類、遷移の予測（「この申請は差し戻されそうか」）の学習データになる。実行者に「AI」を区別して残すことは、AIの判断を後から監査するためにも要る。
- 悪い例→良い例：`status` と `updated_at` しかない → 遷移ごとの行に `actor_type`（human/ai/system）と `reason_code` を持つ。
- 出典：S12（プロセスマイニングは未確認）、【解釈】

### A6. 状態の名前と遷移の意味を、自然言語の説明つきで定義する
- 何を：各状態・各遷移に、業務上の意味と前提条件を短い文章で添える（定義ファイルの description 等）。
- なぜ：【解釈】LLMは状態名のコード値（`HOLD2`）だけでは意味を推測するしかなく、誤った遷移を提案しやすい。人向けの用語集（④）と同じ説明を機械可読な定義に入れておけば、エージェントへの文脈としてそのまま使える。statecharts.dev が「非開発者の理解」を利点に挙げる (S5b) のと同じ理屈が、AIにも当てはまる。
- 悪い例→良い例：`{"HOLD2": [...]}` → `{"on_hold_customer": {"description": "顧客からの追加書類待ち。14日で期限切れへ"}}`。
- 出典：S5b、【解釈】

### A7. 状態図からテストとシミュレーションを作り、AIの振る舞いも同じ図で検証する
- 何を：状態図の全遷移をなぞるテスト（⑤受け入れ条件と連携）を作り、エージェントの行動もモックで同じ遷移をたどれるか検証する。
- なぜ：【確認】statecharts.dev は、QAがステートチャートを「たどれる挙動の地図」として使い、全状態・全遷移を探索したかを確認できると書き、NASA JPL の技術者が赤ペンで全状態・全遷移に印を付けながらテストを書いた例を紹介する。(S5d) 【確認】Stately Agent は、実際のモデルを呼ばずにモックの実行器でロジックを試す仕組み（evals など）を持つとされる。(S4)
- 悪い例→良い例：エージェントの評価を会話のサンプルだけで行う → 「どの遷移を提案し、どれがガードで拒否されたか」を状態図の上で集計する。
- 出典：S5d, S4

### A8. 待ちが長いAI処理は、状態として利用者に見せる
- 何を：AIの処理を「受付→処理中→確認待ち→完了／失敗」の状態として持ち、利用者に見せる。
- なぜ：【確認】AIP-151 の長時間処理（Operation と進捗メタデータ）(S9)、MCP の「ツール呼び出し時に明確な視覚的表示を出す」「呼び出し前に入力を利用者に見せる」(S21)。【解釈】AIの「考え中」をスピナーだけで見せるのではなく、今どの段階か、人の確認を待っているのかを状態として出すと、利用者が介入できる。
- 悪い例→良い例：エージェントが裏で返金を実行し、終わってから報告 → 「返金の提案（承認待ち）」状態で止まり、利用者に承認ボタンを出す。
- 出典：S9, S21

## 4. 越境：それぞれが相手を知るべき理由と配慮

### 4-1. ビジネス・UX がエンジニアリングを知るべき理由
| 知るべきこと | 理由 | 配慮の仕方 |
|---|---|---|
| 状態を一つ増やすと、組み合わせと遷移が掛け算で増える | 【確認】状態爆発 (S5a)。【解釈】「ちょっと一つ足すだけ」が、テスト・権限・通知・集計のすべてに波及する | 表示だけ変えたいのか、規則（遷移・ガード）を変えたいのかを分けて頼む（U1） |
| DBの状態値は減らしにくい | 【確認】PostgreSQL の列挙型は値の削除・並べ替え不可 (S16) | 文言の試行錯誤は表示ラベル側で行い、状態値の追加は慎重に |
| 取り消しには「戻れない点」がある | 【確認】Saga のピボット (S11) | 「いつまでキャンセルできるか」を最初の要件で聞く |
| 状態はすぐには揃わない | 【確認】イベントソーシングは結果整合性を伴う (S12) | 「反映まで数秒かかることがある」前提で画面文言を作る |
| 同時操作の衝突 | 【確認】楽観ロックでは後から保存した側が失敗する (S13, S7) | 衝突時のメッセージと再読み込みの流れをUXとして設計する |

### 4-2. エンジニアがビジネス・UX を知るべき理由
| 知るべきこと | 理由 | 配慮の仕方 |
|---|---|---|
| 状態の切り方が問い合わせを生む | 【解釈】内部では正常な長い待ちが、利用者には「止まっている」に見える（U7） | 長く止まる状態には期待時間と次の出来事を出せるデータ（予定日など）を持たせる |
| 利用者が覚えられるステータスは少ない | 【確認】GOV.UK「最小から始めて調査で増やす」(S17a) | 内部状態をそのまま画面に出さず、表示用の対応表を用意する |
| 例外の状態で人は困る | 【確認】GOV.UK の確認ページ・タスクリストは「次に何が起きるか」「まだ始められない理由」を重視 (S17b, S17c) | 差し戻し・期限切れなどには「理由」の項目を必ず持たせる（理由コード） |
| ビジネスは段階を測りたい | 【解釈】遷移の時刻が残っていないと、後からファネルもリードタイムも測れない（U8） | 遷移履歴を最初から残す（E7） |
| 名前は業務の言葉 | 【解釈】実装者の命名が業務用語として定着してしまう（U9） | 状態名はドメインの人と決め、⑥設計判断として残す |

### 4-3. AI視点から三者が知るべきこと【解釈＋確認】
- ビジネス・UX：AIに任せる範囲は「どの遷移を起こしてよいか」として決められる。【確認】OWASP は影響の大きい行動に人の承認を求める (S22)。「AIにどこまで任せるか」を抽象論でなく、状態図の矢印ごとに決めればよい。
- エンジニア：AIの判断を信じて遷移を許すのではなく、ガードと認可で守る。【確認】「下流のシステムで認可を行う」(S22)、「モデルは提案し、機械が決める」(S4)。
- 全員：遷移履歴に人とAIの区別を残しておくと、AIの判断の質を後から評価できる（A5）。

## 5. ゴールの違いと折り合い

### 5-1. 典型的な対立
| 論点 | UX（利用者の安心と分かりやすさ） | エンジニア（単純さ・正しさ・変更しやすさ） | ビジネス（測定・運用・収益） | 解き方 |
|---|---|---|---|---|
| 状態の細かさ | 利用者の不安を減らすため細かく見せたい | 状態を増やすと爆発するので少なくしたい | 測りたい段階はすべて状態にしたい | **3層に分ける**：内部状態（少なく、規則のため）／表示ラベル（UXが決める、対応表）／計測イベント（遷移履歴から導く）。U1, E2, U8 |
| 状態名 | 利用者の言葉 | 一意で変わらない識別子 | 業務・レポートの言葉 | 内部名は安定した識別子として固定し、表示名と業務名は対応表で持つ。名前の決定理由は⑥に残す |
| 取り消し | いつでも取り消せるようにしたい | 戻れない点の後は取り消せない | 取り消しは売上を減らすので抑えたい | 戻れない点（ピボット）を明示し、その前後で「取り消し」と「返品」を別の遷移にする。期限を画面に出す。E10, U10 |
| 待ちの表示 | 進捗を細かく見せたい | 正確な進捗は出せないことが多い | 問い合わせを減らしたい | 進捗が分かる処理だけ割合表示、分からない処理は「状態＋期待時間」。U5, E12 |
| 例外の扱い | 例外ごとに丁寧な画面 | 例外状態を増やすとテストが増える | 例外の発生率を見たい | 例外は「理由コード」付きの少数の状態にまとめ、文言は理由コードで出し分ける。U6 |
| 履歴 | （関心が薄い） | ストレージと複雑さが増える | 監査・分析に必要 | 全面的なイベントソーシングではなく、まず遷移履歴テーブルから。E7, S12 の「向かない場合」も参照 |
| AIの自動化 | 早く終わってほしい | 誤りが怖い | 人件費を減らしたい | 遷移ごとに「AIが起こしてよい／人の承認が必要／AI不可」を決める。A2 |

### 5-2. 折り合いの付け方の原則【解釈】
1. **「規則」と「見せ方」と「測り方」を別の層にする。** 対立の多くは、同じ「ステータス」を三者が別の意味で使っていることから起きる。3層の対応表を一枚作るだけで、議論が「どの層の話か」に整理される。
2. **状態を足す前に、ガード・並行状態・表示ラベルで代替できないか確かめる。** 【確認】statecharts.dev はガードを「状態を増やさずに条件分岐する手段」として挙げる (S5a)。
3. **決めたことは図と表で残し、変えるときは理由を記録する。** ⑥設計判断の記録と接続する。
4. **測ってから増やす。** 【確認】GOV.UK の「最小から始めて、リサーチで必要と分かったら増やす」(S17a) は、表示ステータスだけでなく内部状態にも当てはまる考え方として使える（この適用は解釈）。

## 6. 建設的な議論の進め方

| 方法 | 何をするか | 誰が | 成果物 | 出典 |
|---|---|---|---|---|
| Event Storming（Big Picture → Process Modelling） | 業務で「起きたこと」を過去形でオレンジの付箋に書き、時系列に並べる。コマンド（青）、アクター（黄小）、ポリシー・制約（黄大）、外部システム（ピンク）、ホットスポット（蛍光ピンク：対立・未解決の問い）を足していく | ドメイン専門家、エンジニア、関係者、中立のファシリテーター。Big Picture は10〜30人 | ドメインイベントの時系列＝遷移のきっかけの一覧、ホットスポット一覧（例外状態の候補） | 【確認】S19a（ddd-crew）, S19b（SAP）。【未確認】Brandolini の書籍本文（Leanpub は開けず） |
| 状態遷移図をみんなで描く | Event Storming で出たイベントを、対象（注文・申請）ごとに「状態」と「矢印」に変換する。矢印ごとに、きっかけ・条件・副作用・実行者（人／AI）・取り消し可否を書く | PdM、UX、エンジニア、QA、運用 | 状態遷移図（ステートチャート）、遷移表 | 【確認】ステートチャートは非開発者との共通言語になる (S5b)、ステークホルダーとの意思疎通に向く (S2) |
| 3層対応表づくり | 内部状態／表示ラベル／KPIの段階を一枚の表にする | UX、エンジニア、ビジネス | 対応表（③分類体系にも入る） | 【解釈】 |
| ジャーニー×状態の重ね合わせ | ジャーニーマップの各段階に内部状態と滞留時間、問い合わせ理由を重ねる | UX、CS、エンジニア | 「不安区間」の一覧と、対策（表示を足す／状態を分ける／通知を送る） | 【解釈】（NN/g のステータストラッカーの議論は未確認） |
| ユーザーストーリーマッピング | 利用者の活動を左から右に並べ（背骨）、各活動の下にストーリーを並べ、最初は端から端まで薄く通る一切れ（ウォーキングスケルトン）から作る | PdM、UX、エンジニア | 例外状態を「いつ作るか」の切り分け | 【未確認】Jeff Patton の原典は開けず、検索結果の二次資料のみ |
| 図をたどるテストレビュー | 状態図の全遷移に印を付けながら、テストと受け入れ条件を確認する | QA、エンジニア、PdM | 遷移網羅のチェックリスト（⑤へ） | 【確認】S5d（JPL の赤ペンの例） |
| 実行可能な状態図の共有 | XState などの定義を可視化して、議論に使った図とコードを一致させる | エンジニア主導、全員が見る | 図とコードが一致した定義 | 【確認】XState は Stately Studio での視覚的な作成・編集を持つ (S1)。django-fsm は遷移のグラフ出力を持つ (S15) |

**議論の進め方の注意【解釈】**
- 最初に「ハッピーパス」だけを描いて合意したくなるが、ホットスポット（例外・対立）を同じ紙の上に残しておく。例外を後回しにすると、例外状態がバラバラに足されて爆発する。
- 矢印ごとに「誰が起こすか（人・AI・時間・外部システム）」を書いておくと、②権限とAIの範囲の議論がその場でできる。
- 名前で揉めたら、内部名と表示名を分けて両方を記録し、先に進む。
