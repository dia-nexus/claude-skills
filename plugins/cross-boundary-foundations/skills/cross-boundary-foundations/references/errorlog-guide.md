# エラーとログの設計手順

SKILL.md の「7. エラーとログ」を、実際に手を動かす順に書いたもの。依頼が「エラーと計測をまとめて」「ログを設計したい」のように、この領域そのものを扱うとき（SKILL.md でいう種類A）に読む。

会員登録フォームを例にとる。メールアドレス、パスワード、生年月日の3つを入れて送る、よくあるフォームだ。これを作るとき、たいてい画面とボタンは決まっているのに、次のことは誰も決めていない。送信して10秒返事がなかったら画面に何を出すか。そのとき登録は済んでいるのか。登録完了率を測りたくなったとき、どの時点を「完了」と数えるか。このあたりは、決めずに渡すと実装する人がその場で決め、後から変えるには過去のデータが足りない。

土台は、note「UXデザイナー/PdMがKPIとログとエラーを理解しないとデータドリブンにならない」（2025年9月26日、https://note.com/art_reflection/n/n2458fe47b286）にある考え方だ。エラーは勝手に出るものではなく、誰かが実装したものなので、いつどう出すかを設計できる。画面に出ない失敗もある。ログはエラーだけの記録ではなく、正常な動きも含めた時系列の記録で、エラーという結果だけ見ても原因は分からない。そして、何を知りたいか（KPI）を決めるのが先で、ログはそれを観測するための仕込みになる。仕込んでいないものは、後から測れない。

括弧の中の ux、engineering、ai は、それぞれ `errorlog-ux.md`、`errorlog-engineering.md`、`errorlog-ai.md` の項目番号を指す。

## 0. 何を知りたいかを先に決める

対象を一つの流れに絞る。フォーム、API、AI 機能、夜間の一括処理など、どれか一つ。

次に、利用者にとっての成功を書く。会員登録フォームなら「アカウントができて、最初の画面に入れた」。その手前で必ず通る地点（入力を始めた、送った、確認メールのリンクを開いた）も並べる。

そのうえで、チームが後から知りたくなりそうなことを3つまで書く。どこで詰まって離脱しているか、障害のときに何が起きていたか、AI の答えがどれだけ使われたか、など。ログの設計はここから逆算する。

## 1. 失敗を棚卸しする

`assets/failure-inventory.md` に、起こりうる失敗を1行に1つずつ書く。

| 列 | 書くこと |
|---|---|
| 失敗 | 何が起きるか（メールアドレスの形が違う、確認メールの送信が失敗する、AI が途中で止まる） |
| 起点 | 利用者の入力か、システムか、外部のサービスか、AI の誤りか |
| 性質 | 一時的か、利用者が直せるか、待てば直るか、人の手が要るか |
| 見え方 | 画面に出るか、出ないか（回り続ける、黙って失敗する、成功の応答なのに中身が誤り） |
| 頻度と重さ | よく起きるか、起きたら何が失われるか |

入力ミスは誰でも思いつくので、思いつきにくい側を意識して探す。

いつまでも終わらない待ちがある。何秒で失敗とみなすかを決めていないと、画面はただ回り続ける（errorlog-ux.md A-11、errorlog-engineering.md A-6）。

結果が分からない失敗がある。送信がタイムアウトしたとき、サーバーでは登録が済んでいるかもしれない。これを「失敗しました」と出すと、利用者はもう一度送り、二重に登録される（errorlog-engineering.md C）。

一部だけ成功した状態がある。アカウントはできたが確認メールが送れなかった、100行のうち3行だけ取り込めなかった、というものだ。

AI の失敗の多くは、成功の応答（HTTP 200）のまま返ってくる。誤った答え、拒否、途中で切れた文章がそうだ（errorlog-ai.md の前提）。

権限や資格がない場合は、入力ミスとは別に扱う。生年月日から年齢の条件を満たさないと分かったとき、「入力が正しくありません」と出すのは誤りだ（errorlog-ux.md A-1）。

## 2. 失敗ごとに、出し方を決める

棚卸しした失敗の一つずつについて、起こさない、気づかせる、直させる、人に渡す、の順に決める。

起こさないために、まず入力の受け付け方を広くする。全角の数字や前後の空白は黙って直し、選べるものは選択式にする（ux A-2）。取り消せない操作の前には、取り消し、確認、見直しのどれかを置く（ux A-3、WCAG 3.3.4）。AI なら、出力の型を構造化出力で仕組みとして守り、繰り返しの上限と止める条件を最初に決めておく（ai E5、E7）。

気づかせるときは、いつ出すかが最初の分かれ目になる。GOV.UK は送信するまで待ち、IBM Carbon は欄を離れたときに出す。入力の途中で責めないこと、一度出したエラーは直した瞬間に消すことは、どちらも同じだ（ux A-4）。どちらにするかは対象の利用者で決め、プロダクト全体でそろえて、判断の記録に残す。

文言は、何が起きたかとどう直せばいいかを、その欄に固有の言葉で書く。メールアドレスなら、形が違うのか、ドメインの綴りが怪しいのか、使えない文字が入っているのかを分けて書き、一つの汎用の文にまとめない（ux A-5）。利用者を責めず、謝りすぎず、エラー番号を前に出さない（ux A-6）。同じ文を、欄のすぐ近くと画面上部の要約の両方に出し（ux A-7）、読み上げソフトにも届くようにする（aria-invalid、aria-describedby、ux A-9）。

エンジニアの側では、プログラムが読むエラーコードと、人が読む文言を分ける。API のエラーは RFC 9457 の形にそろえる（engineering A-2、A-3）。利用者に返す文は一般的なものにし、詳しい原因はサーバーのログに残す（engineering A-4）。

直させるときは、入力した内容を消さない（ux A-8）。一時的な失敗なら、再試行は一つの層だけで行い、間隔を少しずつ空け、回数に上限をつける（engineering A-7、A-8、ai E2）。登録や決済のように二度起きると困る操作は、同じ要求が二度届いても一度しか実行されないようにしてから再試行する（engineering A-9）。失敗し続ける外部サービスは、いったん呼ぶのをやめて早めに失敗を返し、使える機能だけで動かす（engineering A-10）。成功を先に見せる画面にしたなら、失敗したときの巻き戻しと知らせを用意する（ux A-12）。AI の失敗には、別のモデル、小さいモデルや規則、定型文、人、の順に代わりを用意しておく（ai E13）。

人に渡すときのために、利用者に見せる問い合わせ番号をトレース ID と同じにしておく。問い合わせを受けた人が、その番号から該当のログに一直線に辿り着ける（ux A-13、engineering C）。影響の大きい AI の操作は、人の承認を挟む（ai E8）。

最後に、エンジニアの持つエラーの分類と、画面の文言と選択肢を一対一に対応させる。分類は、自動で再試行する、利用者が直せる、待てば直る、サポートに回す、の四つが基本になる。分類コードごとに文言を管理すると、似た失敗で文言がばらばらになることも、文言のない失敗が残ることもなくなる（engineering C）。

## 3. ログを目的ごとに分ける

ログを一種類として設計すると、誰の役にも立たない。目的ごとに分け、それぞれの持ち主と読み手を決める（engineering B-1）。

| 種類 | 何のためか | 主に読む人 | 持ち主の目安 |
|---|---|---|---|
| 運用ログ、トレース、メトリクス | 障害に気づき、原因を探す | エンジニア | エンジニア |
| 監査ログ | 誰がいつ何をしたかを残す | セキュリティ、監査 | エンジニアと法務 |
| 分析イベント | KPI、離脱、継続を測る | PdM、デザイナー、事業側 | PdM |
| AI の評価ログ | AI の誤りを見つけ、品質を見張る | AI を扱う人、PdM | AI を扱う人と PdM |

どの種類にも共通して決めることがある。時刻、レベル、イベント名、サービス名、トレース ID、仮名にした利用者 ID、版といった共通の項目を決めて、構造のある形で残す（engineering B-4）。トレース ID は全サービスに引き継ぐ（W3C Trace Context、engineering B-5）。イベント名は決まった語彙から選び、ID や数字のように変わる値は名前に入れず項目に入れる。イベント名は、分析する人との約束になるからだ（engineering B-7、ux B-3、B-4）。ログレベルがそれぞれ何を意味するかは、チームで決めておく（engineering B-3）。パスワード、トークン、本文、健康の情報のように記録してはいけないものを先に決め、伏せ字にする（engineering B-9）。保存期間と費用も決める。間引いて保存する場合でも、エラーは間引かない（engineering B-10、B-12）。

分析イベントは、元の note 記事の手順で逆算する（ux B-1）。利用者の成功から必須の通過点を出し、通過点のあいだの行動の流れを描き、そこで記録するイベントと項目を決め、最後に KPI の式を書く。`assets/tracking-plan.md` には、1イベント1行で、なぜ取るか（どの KPI のためか）、いつ記録するか、項目、持ち主、版、個人情報を含むかを書く。いつ記録するかは特に食い違いやすい。登録ボタンを押した時点で記録するか、サーバーで登録が済んだ時点で記録するかで、登録完了率はまったく違う数字になる（ux B-5）。

エラーの表示そのものも、分析イベントとして記録する（ux B-6、B-7）。そうすると、どの欄でどれだけエラーが出たか、エラーのあと直せた人と離脱した人がそれぞれどれだけいたか、同じエラーを何度繰り返したかが分かる。エラーが、体験の指標として数えられるようになる。同じ場所を何度も押す、押しても何も起きない場所を押す、といった不満の兆しからは、画面に出ていない失敗が見つかる（ux B-8）。

AI 機能の失敗は、システムのログにはほとんど出ないので、評価と利用者の反応で拾う（ai L7〜L10）。採用した、却下した、直した、作り直させた、コピーした、を、その応答の ID と結んで残す。どれを成功とみなすかは KPI から決める。評価は、出す前（手元のデータで）と出した後（本番の利用で）の両方で行う。AI に採点させるなら、先に人の採点と一致するかを確かめる。プロンプトと応答の本文は、既定では残さない。残すなら別の場所に置き、保存期間、見られる人、学習に使うかとその同意を決めておく（ai L5、L6）。

## 4. AI が読むことを前提に書く

ログを読むのは人だけではなくなった。AI エージェントがログを読み、それを手がかりに次の操作をする。エラー文は、何が起き、次に何をすればいいかを、人にも AI にも分かる形で書く（ai L13）。項目の構造をそろえ、名前を見れば意味が分かるようにし（ai L14）、トレース ID で前後を辿れるようにする（ai L15）。一方で、AI に読ませるログそのものは、信頼できない入力として扱う。利用者の入力がログに混ざっていれば、それが AI への指示として働いてしまうことがある（ai L16）。

## 5. エンジニアに渡す

「このログを取ってください」だけで頼まない（元の note 記事）。

まず、なぜ取りたいのかを渡す。追いたい KPI と、その裏にある利用者の成功だ。次に、何が要るのかを一緒に洗い出す。登録日時、行動した時刻、誰がいつ何をしたか、といった、KPI の計算に必要な情報だ。DB の設計を変える必要があるなら、この段階で分かる。どう実装するかは、エンジニアに任せる。

エラーも同じ順で、失敗の棚卸しと文言の表をエンジニアと一緒に作る。

## 6. 確かめる

ログやイベントの見本（1行に1つの JSON）を `scripts/log_lint.py` にかける。必須の項目の抜け、イベント名の命名、ログレベルの値、イベント名に混ざった ID や数字、メールアドレスや電話番号らしき値、エラーなのに種別がない行、トラッキングプランにないイベントを拾う。出力は成果物に貼る。

`assets/failure-inventory.md` の全行に、出し方、直し方、記録、人への渡し方が埋まっているかを見る。

最後に、実際に失敗させる。ネットワークを切る、外部の API を遅くする、AI に長すぎる入力を渡す、権限のない利用者で開く。棚卸しにない失敗が、たいていここで見つかる。

## 三者で一緒に決めること

どれか一つの職能だけで決めると、ほかの職能の穴になる決めごとがある。

| 決めること | エンジニア | デザイナー | AI を扱う人 |
|---|---|---|---|
| エラーの分類 | 次の行動で分けた分類コード | 分類ごとの文言と選択肢 | AI の誤りをどこまでエラーに含めるか |
| タイムアウト | 何秒で打ち切るか、結果不明の扱い | 待ちの見せ方、「結果を確認する」への導線 | 生成が途中で止まったときの続きの取り方 |
| 問い合わせ番号 | トレース ID を振って全体に通す | 画面での見せ方、サポートへの渡し方 | 応答 ID と評価、利用者の反応を結ぶ |
| 入力の検証 | サーバー側の検証を正とする | いつ出すかと文言 | 構造化出力と出力の検証 |
| 記録する範囲 | 個人情報の伏せ字、保存期間、費用 | 同意の前に送らない、目的に要る分だけ | プロンプトと応答の本文、学習への利用 |
| イベントの持ち主 | 項目の構造と実装 | トラッキングプランの承認と変更の管理 | 評価のイベントの定義 |

## 出すもの

新しく設計するときは、失敗の棚卸し、文言と次の行動の表、トラッキングプラン、ログの共通項目（`assets/log-schema.json` を手直し）、上の「三者で一緒に決めること」の表を出す。

すでにあるものを見直すときは、棚卸しの表で、画面に出ない失敗、結果の分からない失敗、一部だけ成功した状態、AI の誤りが抜けていないかを見る。ログの見本があれば `log_lint.py` にかける。指摘は職能ごとに分けず、失敗ごと、イベントごとに書く。

文言だけを直すときは、ux A-5、A-6 に沿って、何が起きたかとどう直すかを、その欄に固有の言葉で書く。

## 調査ノート

- `errorlog-engineering.md`：エンジニアの観点（エラーは A-1〜A-12、ログは B-1〜B-13）
- `errorlog-ux.md`：デザイナーの観点（エラーは A-1〜A-14、ログは B-1〜B-14。検証のタイミングの流派の違いを含む）
- `errorlog-ai.md`：AI の観点（エラーは E1〜E14、ログは L1〜L16）

各項目には、何をするか、なぜか、悪い例と良い例、出典の URL がついている。【確認】【事実】は出典を開いて確かめたもの、【未確認】は開けなかったもの、【解釈】は調べた担当の考えだ。【未確認】の内容は根拠として使わない。調べた環境では多くの公式サイトが開けず、GitHub 上の原文で確かめている。人に渡す資料で引くときは、公開されている版の URL で一度照らし合わせる。
