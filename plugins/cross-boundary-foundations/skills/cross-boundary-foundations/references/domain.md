## 0. 定義と範囲

**この領域が扱う問い**：「何を何と呼ぶか」「それぞれは何と何がどう関係するか」「その言葉は事業・画面・コード・DB・AI のあいだで同じものを指しているか」。

含むもの：
- 概念モデル（エンティティと関係、ER図、クラス図、オブジェクトマップ）
- 用語集（正式名・別名・定義・使ってよい場面）
- 言葉の一致（事業の言葉／画面の言葉／コードとDBの言葉／AIが参照する語彙）
- 言葉の境界（同じ語が部署や文脈で違う意味になる問題）と、境界のあいだの翻訳
- 名前を変えるときの移行（スキーマ変更、画面文言の変更、用語集の改訂）

隣の領域との分担【解釈】：
- コード値の体系そのもの（区分値、分類の階層）は ③「分類体系とコード値」。ここでは「その分類の名前と定義が一致しているか」までを扱う。
- 状態（ステータス）の名前は ① と重なる。状態遷移はそちら、状態の呼び名の一貫性はこちら。
- 「なぜその名前・その境界にしたか」の記録は ⑥「設計判断の記録」。

キーワードの定義【確認】：
- **ユビキタス言語**：開発者とユーザーのあいだで共通の、厳格な意味を持つ用語を作るプラクティス。ドメインモデルにもとづき、「ソフトウェアは曖昧さをうまく扱えない」ので厳格さが要る（Fowler、bliki-ja訳）。Microsoft の解説では「各境界づけられたコンテキストの中で開発者とドメインエキスパートが一緒につくる共有語彙で、会話・ドキュメント・コードで一貫して使う」とされている。
- **境界づけられたコンテキスト**：大きなシステムを、それぞれが統一されたモデルを持てる単位に分ける DDD のパターン（Fowler、bliki-ja訳）。
- **コンテキストマップ**：コンテキスト同士の関係（どちらが上流か、どう翻訳するか）を描いた図（ddd-crew）。

## 1. エンジニア視点（10項目）

### E1. 業務の言葉を、クラス名・関数名・テーブル名までそのまま通す
- **何をするか**：ドメインエキスパートが会話で使う語を、コードの型名・メソッド名・テーブル名・API のフィールド名に使う。会話で出てこない語がコードにあれば、そのこと自体を議題にする。
- **なぜか**【確認】：Microsoft は「同じ語が会話・ドキュメント・コードのすべてで同じ意味を持つと、誤解が減り、業務の意図を正しく反映したモデルになる」と書く。dotnet の DDD 解説も「大事なのはパターンそのものではなく、コードを業務の問題に沿って組織し、同じ業務用語（ユビキタス言語）を使うこと」としている。Evans は「モデルにもとづく言語が自然に口から出てくるまで満足しないこと」と述べている（Fowler による引用、bliki-ja訳）。
- **悪い例→良い例**【解釈】：営業は「見積」と呼ぶのに、コードは `Proposal`、テーブルは `deal_drafts`、画面は「提案書」。→ 用語集で「見積（Quote）」を正式名に決め、`Quote` 型・`quotes` テーブル・画面「見積」をそろえる。そろえられない箇所は対応表に残す（E8）。
- **出典**：https://github.com/bliki-ja/bliki-ja.github.io/blob/master/_posts/2006-10-31-UbiquitousLanguage.md ／ https://github.com/MicrosoftDocs/architecture-center/blob/main/docs/microservices/model/domain-analysis.md ／ https://github.com/dotnet/docs/blob/main/docs/architecture/microservices/microservice-ddd-cqrs-patterns/ddd-oriented-microservice.md

### E2. 同じ語が部署で違う意味なら、無理に一つにせずコンテキストで分ける
- **何をするか**：「顧客」「製品」「アカウント」のような多義語が出たら、どの部署・どの業務での意味かを確かめ、意味ごとに境界づけられたコンテキストを分ける。
- **なぜか**【確認】：Fowler は電力会社で "meter" が部署ごとに「配電網と地点の接続」「配電網と顧客の接続」「物理的なメーター」と違う意味だった例を挙げ、「こうした多義語は会話ではスムーズに区別できるが、正確なコンピューターの世界ではそうはいかない」「『顧客』や『製品』で何度も混乱を見てきた」と書く。Microsoft も「account のような同じ語が、コンテキストごとに違う意味を持つ」と明記する。
- **悪い例→良い例**【解釈】：全社共通の `customers` テーブルに、営業の「見込み客」、経理の「請求先」、サポートの「問い合わせ者」を全部入れ、`type` 列と NULL だらけの列で区別する。→ 営業コンテキストの「リード」、請求コンテキストの「請求先」、サポートの「問い合わせ者」を別モデルにし、つなぐ ID と対応をコンテキストマップに書く。
- **出典**：https://github.com/bliki-ja/bliki-ja.github.io/blob/master/_posts/2014-01-15-BoundedContext.md ／ MicrosoftDocs domain-analysis.md（上記）

### E3. 「全社で一つの統一モデル」を最初から目指さない
- **何をするか**：一つの巨大な概念モデル・一つの共有DBに全員を合わせる設計を、既定の選択肢にしない。
- **なぜか**【確認】：Fowler は DDD が「大規模システムのドメインモデルを完全に統合することは現実的でなく、費用対効果も高くない」と認めている点を挙げ、代わりにコンテキストごとに統一モデルを持つ（複数の正規化モデル）と説明する。統合データベースについては「すべてのクライアントアプリケーションを考慮したスキーマが必要で、結果として汎用的か複雑か、その両方になる」と書く。
- **悪い例→良い例**【解釈】：用語統一プロジェクトで全部署に「顧客」の定義を一つに合意させようとして半年止まる。→ 共有すべき最小限（顧客ID、法人番号など）だけを共有し、あとはコンテキストごとに定義する。共有部分は Shared Kernel として小さく保つ（E4）。
- **出典**：BoundedContext（上記）／ https://github.com/bliki-ja/bliki-ja.github.io/blob/master/_posts/2004-05-25-IntegrationDatabase.md

### E4. コンテキストのあいだの「翻訳のしかた」を、コンテキストマップに名前で書く
- **何をするか**：二つのコンテキストがつながる箇所ごとに、どちらが上流か、下流が上流の言葉にそのまま従うのか（Conformist）、翻訳層を挟むのか（Anticorruption Layer）、公開の共通語を決めるのか（Published Language）を明記する。
- **なぜか**【確認】：ddd-crew が引用する Evans の DDD Reference によると、Conformist は「上流のモデルに従うことで翻訳の複雑さをなくす。理想のモデルにはならないが統合は大幅に単純になり、上流とユビキタス言語を共有できる」。Anticorruption Layer は「自分のドメインモデルの言葉で上流の機能を提供する隔離層をつくり、内部で双方向に翻訳する」。Published Language は「よく文書化された共通言語を使い、必要に応じてそこへ／そこから翻訳する」。Shared Kernel は「共有するモデルの部分集合を明示的に決め、小さく保ち、相手チームと相談せずに変えない」。また ddd-crew は「大きな一枚より、特定の問いに答える小さなマップ」「使うパターンの意味を事前に説明しておく」ことを勧めている。
- **悪い例→良い例**【解釈】：外部の決済サービスの `status=CAPTURED` を、そのまま自社の画面や集計に流し込む。→ 決済コンテキストとの境界に翻訳層を置き、自社の「入金済み」に対応づける。この関係を「決済（上流）→ 注文（下流、ACL）」とマップに書く。
- **出典**：https://github.com/ddd-crew/context-mapping （Evans の文言は DDD Reference からの引用として掲載。Reference PDF 本体 https://www.domainlanguage.com/wp-content/uploads/2016/05/DDD_Reference_2015-03.pdf は【未確認】）

### E5. エンティティか値オブジェクトかを、「同一性を業務がどう決めているか」で決める
- **何をするか**：ある概念が「同じ値なら同じもの」（金額、期間、住所の値）か、「値が変わっても同じもの」（顧客、出荷、賃貸契約）かを、業務の人に確かめてからモデルにする。
- **なぜか**【確認】：Fowler による Evans の分類の要約では、エンティティは「アイデンティティを持ち、時間経過で形を変える」、値オブジェクトは「属性の組み合わせに意味があり、属性がすべて等しければ同じとみなす」。例としてエンティティは「顧客」「出荷」「賃貸契約」、値は「時間」「お金」。値はイミュータブルにすることが唯一守るべきルールだとしている。値オブジェクトの記事では「2つの点(2,3)は等価とみなすのが理にかなう」「金額は数値と通貨で構成される」と説明している。
- **悪い例→良い例**【解釈】：住所を独立したエンティティ（`addresses` テーブル + ID）にし、引っ越し時に既存住所レコードを書き換えたため、過去の配送記録の宛先まで変わる。→ 配送記録には「その時点の住所」という値を持たせ、顧客の「現住所」とは別に扱う。どちらにするかは「引っ越したら過去の伝票の住所は変わるべきか」を業務に聞いて決める。
- **出典**：https://github.com/bliki-ja/bliki-ja.github.io/blob/master/_posts/2000-01-01-EvansClassification.md ／ https://github.com/bliki-ja/bliki-ja.github.io/blob/master/_posts/2016-11-14-ValueObject.md

### E6. 技術用語そのものの多義に気をつける（「エンティティ」「サービス」）
- **何をするか**：設計の会話で「エンティティ」「サービス」「モデル」と言うとき、DDD の意味なのか、DB のテーブルの意味なのか、SOA やサービス層の意味なのかを最初に断る。
- **なぜか**【確認】：Fowler は「『エンティティ』は一般にデータベースのテーブルやそれに対応したオブジェクトを指す用語」であり、「『サービス』は SOA の意味やサービスレイヤとかぶる」ので、「どの文脈で使われているかに注意する必要がある」と書く。EventStorming の用語集も、業務の人との場では「aggregate（集約）」という語を避け、「constraint（制約）」と呼ぶ方針に変えている。
- **悪い例→良い例**【解釈】：PdM が「エンティティを増やしてください」と言い、エンジニアはテーブル追加、デザイナーは画面上のカード種類の追加と受け取る。→ 用語集の冒頭に「この文書で使う設計用語」を置き、「エンティティ＝業務上の同一性を持つもの（DBテーブルとは限らない）」と書く。
- **出典**：EvansClassification（上記）／ https://github.com/ddd-crew/eventstorming-glossary-cheat-sheet

### E7. 概念モデル（業務の図）と、実装のテーブル設計を分けて描き、対応をつける
- **何をするか**：業務の人と話すための概念モデル（何と何がどう関係するか、1対多か、必須か）と、物理のテーブル設計（中間テーブル、正規化、インデックス）を別の図にし、どの概念がどのテーブルに入っているかを対応表で結ぶ。
- **なぜか**【確認】：デジタル庁の政府相互運用性フレームワーク（GIF）は、データモデルを「基礎編であるコアデータモデル（個人・法人・住所・連絡先など）」と「応用編である実装データモデル」に分け、クラス図・データ辞書・コード一覧を別ファイルで公開している。Fowler の境界づけられたコンテキストの記事も、同じアプリの中で「メモリ内モデルとリレーショナルデータベースモデルの分離」も境界の一種だと述べる。【解釈】物理設計の都合（中間テーブル、`deleted_at` など）が業務の図に混ざると、業務の人は図を読めなくなり、レビューに参加できなくなる。
- **悪い例→良い例**【解釈】：業務レビューに `order_item_option_links` まで載った物理ER図を出す。→ 業務レビューには「注文 1―* 注文明細 *―1 商品」程度の概念図を出し、物理ER図は対応表つきで別に置く。
- **出典**：https://github.com/JDA-DM/GIF （430_コアデータモデル README）／ BoundedContext（上記）

### E8. 名前を変えるときは、一度に切り替えず段階的に移す
- **何をするか**：用語の見直しでテーブル名・列名を変えるとき、「新しい列を作る→両方に書く→古いデータを移す→読み先を切り替える→古い列への書き込みを止める→古い列を消す」という手順を踏む。
- **なぜか**【確認】：strong_migrations（Rails 用のマイグレーション検査ツール）は「使用中の列の名前変更はアプリのエラーを起こす」として、上の6段階を「より安全な方法」として示している。テーブル名の変更も同様に悪い例として挙げている。【解釈】用語を直すコストが高いと、間違った名前が「直せないもの」として固定される。安全な手順を持っておくことが、用語の見直しを議論できる前提になる。
- **悪い例→良い例**：`rename_column :users, :some_column, :new_name` を本番で一発実行（strong_migrations の Bad 例）。→ 6段階で移す。移行中は「旧名＝新名」の対応を用語集にも残す【解釈】。
- **出典**：https://github.com/ankane/strong_migrations （README「Renaming a column」）

### E9. 用語ごとに「定義文」「使い方の注記」を持つデータ辞書を作る
- **何をするか**：用語集を「語の一覧」で終わらせず、各語に定義文（何であるか）、注記（どの場面で使い、何とは違うか）、型や取りうる値、関連する語を書く。
- **なぜか**【確認】：W3C の SKOS 語彙には `definition`（概念の意味の記述や正式な説明）と `scopeNote`（概念の意味や使い方を明確にする注記）が別の項目として用意されている（RDFLib が W3C の skos.rdf から生成した定義で確認）。GIF もコアデータモデルに「データ辞書」と「コード一覧」を付けている。
- **悪い例→良い例**【解釈】：用語集に「会員：サービスの会員」とだけある。→「会員：本人確認を終えてアカウントを持つ個人。注記：メール登録だけの人は『仮登録ユーザー』で、会員に含めない。KPI の会員数もこの定義に従う」。
- **出典**：https://github.com/RDFLib/rdflib/blob/main/rdflib/namespace/_SKOS.py （生成元 https://www.w3.org/2009/08/skos-reference/skos.rdf は直接は【未確認】）／ GIF（上記）

### E10. 用語とコンテキストの定義を、テキストでリポジトリに置いて版管理する
- **何をするか**：コンテキストごとの用語と業務ルールを、コードと同じリポジトリにテキスト（Markdown や DSL）で置き、変更をレビューで通す。
- **なぜか**【確認】：ddd-crew の Bounded Context Canvas には「Ubiquitous Language：このコンテキストにある主要なドメイン用語と、その意味」という欄があり、業務ルール・前提・未解決の問いと並べて書く形になっている。context-mapping のリポジトリは、コンテキストマップをテキストファイルで記述して図を生成する Context Mapper を紹介している。【解釈】Miro やスライドだけに用語集があると、コードの変更と用語の変更がずれても誰も気づかない。
- **出典**：https://github.com/ddd-crew/bounded-context-canvas ／ https://github.com/ddd-crew/context-mapping

## 2. ビジネス・UX視点（10項目）

### U1. 画面を描く前に、業務の出来事を業務の言葉で時系列に並べる
- **何をするか**：関係者全員で、業務で起きる出来事を過去形の付箋（「注文が確定した」「入金を確認した」）で壁に並べ、言葉が食い違った箇所に印（ホットスポット）を付ける。
- **なぜか**【確認】：EventStorming の用語集では、ドメインイベントは「ドメインの専門家にとって意味のある出来事」で「過去形の動詞」で書く。ホットスポットは「（言葉の）不一致、摩擦、疑問、異論」を見える化するためのもの。Big Picture EventStorming の出力からは「浮かび上がる境界づけられたコンテキスト」が見え、境界設計の入口になる。
- **悪い例→良い例**【解釈】：最初の会議で画面のワイヤーを見せ、「この『申込』ボタンで良いですか」と聞く。→ 先に「申込を受け付けた」「審査が通った」「契約が成立した」を並べ、営業の「申込」と法務の「申込」が違う時点を指していることを見つけてから画面の文言を決める。
- **出典**：https://github.com/ddd-crew/eventstorming-glossary-cheat-sheet （Brandolini 本人のサイト https://www.eventstorming.com/ は【未確認】）

### U2. 画面の言葉は、ユーザーの言葉にする。内部の言葉を漏らさない
- **何をするか**：エラー文、ラベル、ステータス表示に、DB の列名・内部コード・技術用語を出さない。
- **なぜか**【確認】：GOV.UK Design System のエラーメッセージのガイドは、「form post error」「unspecified error」「error 0x0000000643」のような技術用語を使わないこと、平易な英語で何が起きたかと直し方を書くことを求めている。404 / 500 ページでも「404」「bad request」といった用語を避けるよう書いている。
- **悪い例→良い例**：「入力エラー：addr_line1 is required」→「住所1行目を入力してください（建物名と番地など）」（GOV.UK の例「Enter address line 1, typically the building and street」に倣った【解釈】）。
- **出典**：https://github.com/alphagov/govuk-design-system/blob/main/src/components/error-message/index.md

### U3. 画面の言葉と内部の言葉が違ってよい場合は、対応表で明示する
- **何をするか**：ユーザー向けの呼び名（画面）と業務・内部の正式名がどうしても違うとき、用語集に「画面での表示名」「別名」「内部名」を並べて書く。
- **なぜか**【確認】：SKOS は一つの概念に `prefLabel`（その言語での優先ラベル）、`altLabel`（別のラベル）、`hiddenLabel`（表示には出さないが全文検索では使えるラベル）を持たせる設計になっている。【解釈】「言葉をそろえる」は「全部同じ文字列にする」ではなく、「同じ概念を指していると誰でも辿れる」状態のこと。ユーザーの言葉（U2）と業務の厳密さ（E1）を両立させる現実的な方法がこの対応表である。
- **悪い例→良い例**【解釈】：画面は「お気に入り」、DB は `bookmarks`、分析ダッシュボードは「保存数」、サポートの手順書は「ブックマーク」で、誰も同一だと書いていない。→ 用語集に「概念：保存（Saved item）／画面表示：お気に入り／内部名：bookmark／別名：ブックマーク、保存数（指標）」と一行で結ぶ。
- **出典**：RDFLib _SKOS.py（上記）

### U4. オブジェクトを先に洗い出してから画面を作る（OOUX / ORCA）
- **何をするか**：ユーザーが扱う「もの」（オブジェクト）、その関係、それぞれへの操作（CTA）、属性を、画面設計の前に洗い出す。
- **なぜか**：【未確認】ooux.com の一次資料は開けなかった。検索結果の要約（LogRocket 等の二次記事）では、OOUX は Sophia V. Prater が提唱し、ORCA は Objects・Relationships・CTAs・Attributes の頭文字で、繰り返し回すことで理解を深める、と説明されている。この要約は一次資料で確かめていないので、スキルに書く前に https://ooux.com/ と Prater の原稿（A List Apart「Object-Oriented UX」等）で確認が必要。
- **【解釈】**：ORCA の O・R・A は、エンジニアの ER図（エンティティ・関係・属性）とほぼ同じ形をしている。UX 側から ER図に入る入口として使えそう、というのは調査担当の解釈で、出典の主張ではない。
- **悪い例→良い例**【解釈】：画面一覧から作り始め、「検索結果画面」「詳細画面」「マイページ」ごとに同じ「講座」が違う属性・違う呼び名で出てくる。→「講座」「講師」「受講者」「申込」をオブジェクトとして先に定義し、どの画面でも同じ名前・同じ属性で出す。
- **出典**：【未確認】https://ooux.com/ ／ 検索で見つけた二次資料 https://blog.logrocket.com/ux-design/object-oriented-ux-ooux/ （本文も未確認）

### U5. ユーザーのメンタルモデルと、システムの概念モデルのずれを調べる
- **何をするか**：ユーザーが「これは何で、何とつながっているか」をどう思っているかを調べ、システム側の概念モデルとのずれを洗い出す。
- **なぜか**：【未確認】NN/g の mental models 記事（https://www.nngroup.com/articles/mental-models/）と Don Norman『誰のためのデザイン？』の「概念モデル」の記述は、今回開けなかった。定義や引用はスキルに書く前に原文で確認すること。
- **【解釈】**：DDD 側の「ドメインエキスパートとの会話でユビキタス言語を検証する」（E1 の Evans の引用）は、業務の専門家の頭の中のモデルとコードのモデルを合わせる話で、UX の「ユーザーのメンタルモデル」と同じ構造の問題を、別の相手（業務の人 vs エンドユーザー）について扱っている。両者を並べると、合わせるべきモデルは少なくとも三つ（エンドユーザー／業務／実装）ある。
- **出典**：【未確認】上記2点

### U6. 用語集には「どの部署・どの文脈での意味か」を必ず書く
- **何をするか**：多義語は一つの定義に押し込めず、「営業での『顧客』」「経理での『顧客』」のように文脈ごとに定義を分け、どこで使い分けるかを書く。
- **なぜか**【確認】：E2 の通り、Fowler は部署ごとに微妙に違う言葉を使うことが統一モデルの障害になると書き、Microsoft は「各コンテキストは独自のユビキタス言語を持てる」とする。Bounded Context Canvas も用語欄をコンテキストごとに持つ。
- **悪い例→良い例**【解釈】：全社用語集に「顧客：当社と取引のある者」。→「顧客（営業）：商談中を含む取引相手の法人」「顧客（請求）：請求書の宛先となる法人。親会社一括請求の場合は親会社」「顧客（サポート）：問い合わせをした個人」。
- **出典**：BoundedContext／domain-analysis.md／bounded-context-canvas（上記）

### U7. 指標（KPI）の名前と計算式を一か所で定義する
- **何をするか**：「売上」「アクティブユーザー」などの指標を、部署やBIツールごとに計算させず、一か所で定義してそこから参照する。
- **なぜか**【確認】：dbt のドキュメントは、指標の定義を BI 層からモデリング層に移すことで「異なる事業部門が、どのツールを使っていても同じ指標定義で作業していると確信できる」「定義を変えれば、使われている所すべてに反映される」と説明する。
- **悪い例→良い例**【解釈】：経営会議の「売上」は税込・返品前、マーケのダッシュボードは税抜・返品後、同じ「売上」という名前で数字が合わない。→ `revenue_net`（税抜・返品後）を正式定義にし、別の指標は別の名前を付ける。
- **出典**：https://github.com/dbt-labs/docs.getdbt.com/blob/current/website/docs/docs/use-dbt-semantic-layer/dbt-sl.md

### U8. ビジネス・UX側も、ER図を「読める」ところまでは身につける
- **何をするか**：自分で設計できなくてよいので、箱（エンティティ）、線（関係）、1対多・多対多、必須／任意の区別を読めるようにする。
- **なぜか**【確認】：note 記事「UXデザイナー/PdMがKPIとログとエラーを理解しないとデータドリブンにならない」（2025-09-26）の「むすびに」に、「例えばそもそもER図の読み方わからないと厳しかったり、SQLかけた方が良かったり、1秒間に数万〜数百万回アクセスがあるサイトの全てのログを取るのは現実的じゃなかったり、コスト最適化が必要だったり。」とある。【解釈】ログやKPIの設計は「何が何に紐づいているか」の上に成り立つため、ER図が読めないと、計測したいことがそもそもデータとして取れるかを判断できない。
- **悪い例→良い例**【解釈】：PdM が「ユーザーごとの講座完了率」を要求したが、受講記録が「申込」にしか紐づいておらず、家族アカウントでは誰が受講したか分からない構造だった、とリリース後に判明。→ 要件の段階で概念図を一緒に見て「受講者」と「申込者」が別の箱かを確認する。
- **出典**：https://note.com/art_reflection/n/n2458fe47b286

### U9. 用語が広まるほど意味は崩れる前提で、定義の原典へ戻れるようにする
- **何をするか**：社内で流行った言葉（「アクティブ」「オンボーディング完了」など）は、定義の原典（用語集の該当行）へのリンクを資料に付けて使う。
- **なぜか**【確認】：Fowler は「意味の希薄化」を「個人やグループが適切に定義した用語が、歪められた定義のままコミュニティに広まること」とし、伝言ゲームのように「発案者まで戻らない限り、用語の重要な意味が失われる」、「具体的な技術より幅広い概念のほうが起きやすい」と書く。
- **悪い例→良い例**【解釈】：「アクティブユーザー」が部署を渡るうちに「ログインした人」「何か操作した人」「課金した人」に分かれる。→ 資料で使うたびに用語集のリンクを付け、定義を変えるときは変更履歴を残す。
- **出典**：https://github.com/bliki-ja/bliki-ja.github.io/blob/master/_posts/2006-12-14-SemanticDiffusion.md

### U10. 公共の標準語彙があるものは、自分たちで発明しない
- **何をするか**：個人・法人・住所・連絡先・日付のように、社会全体で共通の概念は、既存の標準データモデルや語彙を土台にする。
- **なぜか**【確認】：GIF は「データの連携・交換のためのデータ参照モデル」で、そのまま採用するほか、拡張や項目の取捨選択などのカスタマイズをして使えるとしている。ddd-crew は Published Language の例として iCalendar や vCard を挙げる。
- **悪い例→良い例**【解釈】：住所を自由入力の1列にし、後で自治体データや配送業者と連携できない。→ GIF の住所モデルを参照して項目を分け、使わない項目は落とす。
- **出典**：https://github.com/JDA-DM/GIF ／ context-mapping（上記）

## 3. AI視点（8項目）

### A1. 用語集を、正式名・別名・定義が分かれた構造データとしても持つ
- **何をするか**：人が読む用語集と同じ内容を、正式名（prefLabel）、別名（altLabel）、検索用の表記ゆれ（hiddenLabel）、定義、注記、上位／下位／関連語の項目を持つ機械可読な形（YAML、JSON、SKOS など）でも持つ。
- **なぜか**【確認】：SKOS は「シソーラス、分類体系、件名標目表、タクソノミー、用語集や専門用語集に埋め込まれた概念体系」の基本構造を記述する語彙であり、上記の各項目と `broader`（より一般的な概念）／`narrower`／`related` を持つ。【解釈】RAG やエージェントに用語集を渡すとき、表で書かれた用語集より、項目が分かれていたほうが「別名で検索された語を正式名に寄せる」処理を組みやすい。
- **悪い例→良い例**【解釈】：社内Wikiの用語集が自由記述で「お気に入り（ブックマークとも言う）」。→ `{pref: "お気に入り", alt: ["ブックマーク", "保存"], hidden: ["おきにいり"], definition: ..., context: "会員アプリ"}`。
- **出典**：RDFLib _SKOS.py（上記）

### A2. 同一性を「名前」ではなく ID で決める（AIは表記が違えば別物、同名なら同一と扱いがち）
- **何をするか**：AI に文書からエンティティを抽出させる場合や、複数のデータを AI に結合させる場合、同じものかどうかの判断を名前の一致に任せず、ID や対応表で決める。
- **なぜか**【確認】：Microsoft の GraphRAG では、テキスト単位ごとに抽出したサブグラフを統合するとき「同じ title と type を持つエンティティは、説明を配列にしてマージする」。【解釈】これは、名前がそろっていれば正しく一つにまとまる一方で、「顧客」と「お客様」は別ノードのまま残り、逆に意味の違う同名の「顧客」（営業と請求、E2）は一つに合体してしまう、ということを意味する。用語がそろっていない組織の文書を入れると、知識グラフに組織の言葉の乱れがそのまま写る。
- **悪い例→良い例**【解釈】：社内文書を丸ごと GraphRAG に入れ、「顧客数は？」と聞く。→ 抽出の前に用語集の別名を正式名に寄せる処理を入れるか、プロンプト調整で用語集を渡す。GraphRAG 自身も「そのままでは最良の結果にならないことがある」としてプロンプト調整を強く勧めている【確認】。
- **出典**：https://github.com/microsoft/graphrag/blob/main/docs/index/default_dataflow.md ／ https://github.com/microsoft/graphrag/blob/main/README.md

### A3. AI に生のテーブルを推測させず、定義済みの指標・エンティティを通して答えさせる
- **何をするか**：AI がデータに答えるとき、生のテーブルに直接 SQL を書かせるのではなく、セマンティックレイヤー（指標・ディメンション・エンティティの定義）経由で問い合わせさせる。
- **なぜか**【確認】：dbt のドキュメントは、Claude や ChatGPT のような AI ツールが dbt MCP サーバー経由でセマンティックレイヤーにつながることで、「生のテーブルを推測する代わりに、管理された指標を使って答える」と書く。dbt MCP サーバーは `list_metrics`、`get_dimensions`、`get_entities`、`query_metrics` などのツールを提供する。dbt のエンティティは「顧客、取引、広告キャンペーンなど事業の現実の概念」で、セマンティックモデル間の結合キーになる。
- **悪い例→良い例**【解釈】：AI が `orders` と `order_items` を独自に結合し、返品を引かない「売上」を答える。→ AI には `revenue_net` という定義済み指標だけを使わせる。
- **出典**：https://github.com/dbt-labs/docs.getdbt.com/blob/current/website/snippets/_sl-connect-your-ai.md ／ https://github.com/dbt-labs/dbt-mcp ／ https://github.com/dbt-labs/docs.getdbt.com/blob/current/website/docs/docs/build/entities.md

### A4. AI に渡すスキーマやツールには、名前だけでなく説明文を書く
- **何をするか**：テーブル・列・API・ツールの定義に、何を表すか、いつ使うか（使わないか）、各パラメータの意味、制約を説明文として書く。
- **なぜか**【確認】：Anthropic のツール定義のガイドは「非常に詳しい説明を書くこと。これがツールの性能にとって群を抜いて最も重要な要素」とし、何をするか、いつ使うか／使わないか、各パラメータの意味、注意点や制約を書くよう求めている。
- **悪い例→良い例**【解釈】：列名 `flg2`、説明なし。→ `is_trial_member`：「無料体験中の会員なら true。体験終了日の翌日0時に false。会員数（KPI）には含めない」。
- **出典**：https://platform.claude.com/docs/en/agents-and-tools/tool-use/define-tools

### A5. 名前にコンテキストを含めて、AIが取り違えない一意な名前にする
- **何をするか**：複数のコンテキストやサービスにまたがる名前には、コンテキスト名を接頭辞として付ける。AI に返す識別子は、意味のある安定した ID にする。
- **なぜか**【確認】：同じガイドは「ツールが複数のサービスやリソースにまたがるときは、名前にサービスの接頭辞を付ける（例：`github_list_prs`、`slack_send_message`）。ライブラリが大きくなってもツール選択が曖昧にならない」とし、応答では「不透明な内部参照ではなく、意味のある安定した識別子（スラッグや UUID）を返す」よう勧めている。【解釈】これは境界づけられたコンテキスト（E2）を名前に刻むことと同じ発想で、人間には文脈で区別できる多義語を、AI には名前で区別させる。
- **悪い例→良い例**【解釈】：`get_customer` が営業CRMと請求システムの二つにある。→ `sales_get_lead`、`billing_get_payer`。
- **出典**：上記 define-tools

### A6. 別の体系との対応づけには「どれくらい同じか」を区別して書く
- **何をするか**：他部署や他社の用語・コードと対応づけるとき、「完全に同じ」と「ほぼ同じ（場面によっては置き換え可）」を区別する。
- **なぜか**【確認】：SKOS では `exactMatch` は「広い範囲の検索用途で置き換え可能だと高い確度で言える」対応で推移的（A=B かつ B=C なら A=C）。`closeMatch` は「一部の用途では置き換え可能なほど似ている」対応で、三つ以上の体系をまたいで対応を組み合わせたときの「誤差の累積」を避けるため、推移的とは宣言されていない。
- **悪い例→良い例**【解釈】：自社の「会員」＝ A社の「ユーザー」＝ B社の「アカウント」を全部「同じ」で結び、AI が会員数と B社アカウント数を足してしまう。→「会員 closeMatch ユーザー（注記：A社は仮登録を含む）」のように確度と注記を付ける。
- **出典**：RDFLib _SKOS.py（上記）

### A7. AI に読み書きさせる状態は、ドメインの言葉でできたテキスト記法で持つ（MNP）
- **何をするか**：アプリの状態を、AI が読み書きしやすいテキスト記法（DSL）で持ち、システムプロンプトにその記法と概念の説明を入れる。記法の語彙を、そのドメインの用語集と一致させる。
- **なぜか**【確認】：MNP（中間記法パターン）を紹介する note 記事は、「LLMはテキストを扱うのが得意で、GUIを扱うことはあまり得意ではありません」とし、GUI を直接操作させると「毎回出力が違います」「差分修正ができず」と述べる。方針は「GUIの背後にある意味状態をテキスト化し、AIはその意味状態を更新する」こと。システムプロンプトでは役割・概念説明・記法の3つを定義する。構成要素は記法（DSL）・パーサー・シリアライザー・システムプロンプト。
- **【解釈】**：MNP の「記法」は、その道具にとってのユビキタス言語そのものになる。記法の要素名が業務の言葉とずれていると、AI は記法の言葉で考え、ユーザーは業務の言葉で頼むので、プロンプトのたびに翻訳が起きる。記法を設計するときに、用語集（E9・A1）とコンテキスト（E2）を先に決めておくと、AI・画面・コードの三者が同じ語で動く。
- **出典**：https://note.com/art_reflection/n/nccfe6cc57073

### A8. AI が作った用語・関係は、そのまま正にせず人がレビューする
- **何をするか**：LLM に文書から用語集やエンティティ・関係を抽出させた結果は「下書き」として扱い、ドメインの人が確認してから正式な用語集・概念モデルに入れる。
- **なぜか**【確認】：GraphRAG は「そのままのデータでは最良の結果にならないことがある」としてプロンプト調整を強く勧め、コードは「デモであり公式にサポートされた製品ではない」と書いている。【解釈】抽出は名前で同一性を判定しがちで（A2）、組織の言葉の乱れを固定してしまう。Evans の「ドメイン専門家は不自然な用語に異を唱えるべき」（E1 の引用）は、AI 抽出結果のレビューにもそのまま当てはまる。
- **出典**：graphrag README／docs/index.md（上記）

## 4. 越境：それぞれが相手を知るべき理由と配慮

### (a) ビジネス・UX がエンジニアの視点（概念モデル・用語の厳密さ）を知るべき理由
- 【確認】「多義語は会話では区別できるが、コンピューターの世界ではそうはいかない」（Fowler, E2）。会議で通じていた言葉が、実装の段階で一つに決めざるを得なくなる。その決定をエンジニアだけにさせると、業務の意図と違う方に倒れる。
- 【確認】元の note 記事の指摘（U8）：ER図が読めないと、ログ・KPI がそもそも取れる構造かを判断できない。
- 【解釈】名前の変更には実装コスト（E8 の6段階）がかかる。初期に言葉を詰めることは、後で安く直すための投資である。
- **配慮**【解釈】：設計に口を出すためではなく、「これとこれは同じものですか」「1対多ですか」と聞けるようになるために学ぶ。概念図の段階（E7）で入れば、物理設計の知識はいらない。

### (b) エンジニアがビジネス・UX の視点を知るべき理由と、どう配慮するか
- 【確認】ユビキタス言語は「開発者とドメインエキスパートが一緒につくる」もので、Evans は「ドメイン専門家は不自然な、ドメインの理解を妨げる用語や構造に異を唱えるべきで、開発者は設計の妨げになる曖昧さや矛盾に注意を払う」と役割を分けている（E1）。言葉の正しさの判定者は業務側にある。
- 【確認】ユーザーに見える言葉は、技術用語ではなくユーザーの言葉で書く（U2、GOV.UK）。DB の名前が正しくても、画面にそのまま出せるとは限らない。
- 【未確認】ユーザーのメンタルモデル（U5）や OOUX（U4）の知見は、今回一次資料で確認できていない。
- **配慮**【解釈】：
  - 業務の人との場では DDD の専門用語を減らす。EventStorming 自体が「aggregate」を業務の人向けに「constraint」へ言い換えた（E6）のが手本になる。
  - 「正しい名前」を押し付けず、画面表示名・業務名・内部名の三つを対応表で結ぶ（U3）。
  - 用語の変更を頼まれたとき「DBが変わるから無理」で終わらせず、段階的移行の手順とコストを示す（E8）。

### (c) AI の視点を三者が知るべき理由
- 【確認】AI は与えられた名前と説明を手がかりに動く。ツールの説明文が性能の最重要要素であり（A4）、知識グラフの構築では同じ名前・同じ種類のものがまとめられる（A2）。
- 【解釈】人間は文脈で多義語を読み分け、表記ゆれを無意識に吸収する。AI はその吸収を、明示された用語集・ID・コンテキストの接頭辞がある範囲でしかできない。つまり、人間同士なら許されていた用語の乱れが、AI を入れた瞬間に誤答や重複集計として表に出る。
- 【解釈】逆に、用語集・概念モデルをきちんと持っている組織は、それをそのまま AI の参照資料（RAG の辞書、セマンティックレイヤー、MNP の記法）に流用できる。④は「AI のデータ資源」として最も再利用しやすい領域の一つ。

## 5. ゴールの違いと折り合い

### 典型的な対立【解釈】（各行の根拠は1〜3章の該当項目）

| 争点 | ビジネス（事業）の言い分 | UX の言い分 | エンジニアの言い分 | AI 活用の言い分 | 解き方 |
|---|---|---|---|---|---|
| 何と呼ぶか | 社内で通じる業務用語・契約用語にしたい | ユーザーが使う言葉にしたい（U2） | 一意で厳密な名前にしたい（E1） | 機械が取り違えない一意な名前・IDにしたい（A5） | 概念は一つ、ラベルは複数。正式名・画面表示名・内部名・別名を対応表で結ぶ（U3, A1） |
| 一つの言葉に一つの意味か | 部署ごとに意味が違って当然 | ユーザーには一つに見せたい | 一つの意味に固定したい | 同名は同一として処理されてしまう（A2） | コンテキストごとに定義を分け（E2, U6）、名前にコンテキストを刻む（A5）。全社統一は最小限（E3） |
| いつ決めるか | 走りながら決めたい | 調査で分かってから決めたい | 実装前に決めたい（後から直すと高い） | 学習・索引の前に決めたい | 早期に EventStorming で仮決め（U1）、変更は段階的移行で安くする（E8）、用語集は版管理（E10） |
| 指標の定義 | 部門ごとの見せ方がほしい | ユーザー行動に即した定義がほしい | 計算式は一か所に | AIに推測させたくない | 正式定義を一か所に置き（U7）、別定義には別名を付ける。AIは定義済み指標経由（A3） |
| どこまで標準に合わせるか | 自社の強みは独自概念にある | ユーザーにとって自然なら何でもよい | 標準に合わせて連携を楽にしたい | 公共の語彙に乗るとAIも外部データと結べる | 汎用概念（住所・法人等）は標準を土台（U10）、差別化の核は独自に。上流に従うか翻訳層を挟むかをマップに書く（E4） |
| 用語集の重さ | 作っても誰も読まない | 現場の言葉が反映されない | 更新されず腐る | 構造化されていないと使えない | 人が読む版と機械可読版を同じ原本から作る（A1, E10）。用語集の行に持ち主と更新日を付ける |

### 折り合いのための原則【解釈】
1. **「言葉をそろえる」を「同じ概念に辿れる」に読み替える。** 文字列の統一ではなく、対応の明示を目標にすると、三者の言い分は大半が両立する（U3）。
2. **争う単位をコンテキストにする。** 「顧客の定義」を全社で争わず、「請求コンテキストでの顧客」を決める（E2, E3）。
3. **言葉の判定者と、名前の実装者を分ける。** 意味が正しいかは業務・UX、一意性と移行はエンジニア、機械可読性は AI 担当が責任を持つ（Evans の役割分担、4章(b)）。
4. **変更を安くしてから議論する。** 段階的移行（E8）と版管理（E10）があれば、「今は仮の名前で進め、分かったら直す」が現実的な選択肢になる。

## 6. 建設的な議論の進め方

### 6-1. 出来事から始める（EventStorming）【確認】
- 業務の専門家とエンジニアなど、知識を持つ人と知識が必要な人の両方を招く。
- 各自が出来事（過去形）を書いて並べる「混沌とした探索」→ 時系列をそろえて重複を除く「タイムラインの強制」。
- 言葉の不一致・疑問・異論はその場で議論し尽くさず、ホットスポットとして貼って先に進む。ファシリテーターは中立で、長い議論を切ってホットスポットにするのが役目。
- 合意事項として Deep Democracy の「全員が正しい。誰も真実を独占していない」「一緒に学ぶ意思を持つ」などを貼り出す例が示されている。
- Big Picture の結果から「浮かび上がる境界づけられたコンテキスト」を見つける。
- 出典：https://github.com/ddd-crew/eventstorming-glossary-cheat-sheet

### 6-2. 発見から設計までの順番（DDD Starter Modelling Process）【確認】
- 「発見（Discover）は飛ばせない。チーム全体がドメインを理解しないと、ソフトウェアの判断はすべて的外れになる」。発見は継続的に行う。
- 道具として Domain Storytelling、Example Mapping、EventStorming、User Journey Mapping、User Story Mapping が並ぶ。【解釈】UX 側の手法（ジャーニーマップ、ストーリーマップ）が DDD の発見の道具として同列に扱われており、越境の入口になる。
- 関わる人：ソフトウェアを設計・実装・テストする人、ドメイン知識を持つ人、製品と事業戦略を理解する人、顧客のニーズを理解する人、そして代理ではない実際のエンドユーザー。
- 出典：https://github.com/ddd-crew/ddd-starter-modelling-process

### 6-3. コンテキストごとに一枚にまとめる（Bounded Context Canvas）【確認】
- 名前と目的（業務の言葉で、技術の話はしない）、ユビキタス言語、業務上の決定（ルール・方針）、前提、検証の指標、未解決の問いを一枚に書く。
- 「未解決の問い」が多いことは、その境界の不確かさの目安になる。
- 出典：https://github.com/ddd-crew/bounded-context-canvas

### 6-4. オブジェクトから画面へ（OOUX / ORCA）【未確認】
- ORCA のラウンドの進め方、成果物（オブジェクトマップ等）は一次資料未確認。スキルに入れる前に ooux.com で確認すること。

### 6-5. 用語集の作り方と持ち主【解釈】（確認済みの要素を組み合わせた提案）
1. **材料**：EventStorming の付箋とホットスポット（6-1）、既存の画面文言、DB の列名、問い合わせログの言葉を集める。
2. **一行の形式**：概念ID／コンテキスト／正式名／画面表示名／別名・表記ゆれ／定義／注記（何とは違うか）／関係（上位・関連）／他体系との対応と確度／持ち主／更新日。SKOS の項目（A1, A6, E9）と Bounded Context Canvas の用語欄（6-3）を合わせた形。
3. **置き場所**：リポジトリにテキストで（E10）。人が読む表と、AI 向けの構造データを同じ原本から出す。
4. **持ち主**：コンテキストごとに一人。意味の判定は業務・UX 側、名前の一意性と移行計画はエンジニア側（5章の原則3）。
5. **変更の流れ**：変更提案 → 影響範囲（画面・DB・指標・AI の辞書）を一覧 → 段階的移行（E8）→ 用語集の旧名を別名として残す。
6. **AI での点検**：AI に新しい仕様書を読ませ、用語集にない語・別名で書かれた語を列挙させて、用語の乱れを早めに見つける（A2 の裏返しの使い方）。

### 6-6. 議論の作法【解釈】
- 「その言葉、どの部署の意味で言っていますか」を責める質問にしない。多義は組織に普通にあるもの（Fowler の meter の例）として扱う。
- 決まらない言葉は、仮の名前とホットスポットで先に進め、未解決の問いとして残す（6-1, 6-3）。
- 図は問いごとに小さく（ddd-crew の「特定の問いに答える小さなマップ」）。全部入りの ER図で会議をしない（E7）。
